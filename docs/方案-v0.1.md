# claude-gateway 方案 v0.1

日期：2026-10-27。状态：**设计阶段，部分定稿**，尚无实现。已定事项见 §0.1；开放设计问题见 §11。

源码证据和版本锁定见[参考项目源码调研](research/参考项目源码调研.md)，下文“调研 §x”均指该文档。会话与模型切换的专题设计见[会话管理与模型切换](会话管理与模型切换.md)。

设计前比较过 CCR 仅网关模式、LiteLLM、NewAPI / Bifrost 等现有方案。在“数据和密钥自控、协议转换可审计”优先的前提下，本项目选择自建一层独立的 Messages 薄转发层，本方案是它的扩展版设计。

## 0. 一页结论

- **定位**：一个人自己部署，让 **Claude 桌面端（Code 模式）** 和 Claude Code 顺畅使用国产模型的网关。单部署、单使用者；部署在自己的服务器上，通过公网 HTTPS 访问。
- **第一接入对象是桌面端 Code 模式**，CLI 版 Claude Code（cc）同时支持。桌面端的约束（模型 ID 形态、模型发现、窗口推断）见[桌面端接入](桌面端接入.md)。
- **纯透传**：网关默认不改请求和响应，只做必要的兼容改写，每处改写都记录诊断（§1.2）。
- **优先保证服务器部署**。
- **安全是第一优先级**：
  - 网关自己签发访问 key，上游真实 key 只放在服务器上。
  - 强制 HTTPS，认证失败快速拒绝并记录。
  - 按 key 和 IP 限流，IP 白名单可选，日志脱敏（§8.4）。
- **本期重点**是“与 cc 的兼容”和“与模型的交互”：协议保真、国产模型差异、会话与模型切换、缓存。
- **首批上游**为四个渠道：DeepSeek 官方、智谱 GLM 普通 API、智谱 GLM Coding Plan、火山方舟 Coding Plan。**四家都有原生 Anthropic 兼容端点**（§5.2），所以本期主路径全部是原生透传加 compat profile，OpenAI 格式转换（原 M3）降为备用。
- **模型 × 渠道，显式选择**：同一个模型可能有多条渠道，例如 DeepSeek V4 Pro 既可以走官方，也可以走火山方舟 Coding Plan。每个“模型 × 渠道”配一个对外 ID，在桌面端分别列出；一个对外 ID 固定对应一个“模型 × 渠道”。用哪个由用户在客户端选择（§4.8、§5.3）。
- **内部格式选 Anthropic Messages**；差异处理借鉴 dsh / pi-ai 的声明式 compat profile；每一处改写都记录诊断，不做静默丢弃。
- **场景与模型的对应由客户端的档位配置决定**：后台小任务、子 agent、opusplan 分别用哪个对外 ID，由桌面端的 tier 和 cc 的 `ANTHROPIC_DEFAULT_*_MODEL` 决定；网关生成这些配置片段（§4.9）。
- **错误原样返回**：上游失败（含 Coding Plan 额度用完）时，网关把错误返回给客户端，只做已登记的措辞兼容改写（§1.2）。
- **Coding Plan**：各家 Coding Plan 对使用范围有限制，使用者需自行阅读并遵守官方条款；本项目不提供、也不鼓励转售、共享或池化（§6.3）。
- **技术栈**：Node.js 22+ / TypeScript / undici（已定）。
- 本期范围之外的内容集中列在 §12“边界”。

## 1. 定位、目标与原则

### 1.1 目标

1. Claude 桌面端（Code 模式）和 cc 通过一个公网 HTTPS 地址，按会话或场景使用首批四个渠道的模型。桌面端是第一接入对象。
2. 协议层兼容要可审计：代码自己掌握，转换规则可读，有回归用例。
3. 对话正文和上游密钥由部署者自己掌控：网关跑在部署者自己的服务器上，上游 key 只留在服务器上。
4. 公网暴露下的安全：只有持有网关 key 的部署者本人客户端能调用，攻击面最小。
5. 会话与模型切换行为正确，缓存保持命中，长会话能正常自动压缩。

### 1.2 纯透传原则

网关默认**原样转发**请求和响应（字节级，包括 `usage`、SSE 事件、错误体），只做下列**必要的兼容改写**。每一处改写都产生一条诊断，写入请求日志：

| 改写 | 原因 | 细节 |
|---|---|---|
| 认证头替换 | 客户端持有的是网关 key，要换成上游 key | §3、§8.4 |
| 模型名映射，以及 `message.model` 回显对外 ID | 桌面端要求 Claude 形态的模型 ID；cc 按 `message.model` 判断是否换了模型 | §4.8、[桌面端接入 §6](桌面端接入.md#6-对网关设计的影响) |
| 已知的非 Anthropic 超长错误改写为 cc 能识别的措辞 | 否则 cc 不触发压缩，会话卡死 | [桌面端接入 §4.3](桌面端接入.md#43-超长错误典型问题与网关的必要改写) |
| 签名类错误改写为 cc 能识别的措辞；用户切换模型后，去掉目标渠道无法接受的 thinking 块 | cc 只剥带签名的异源块，其余块可能让目标渠道报错 | 会话专题 §4.2 |
| 上游 tool_use id 不符合 Anthropic 格式时做可逆编码（如 M0 证实需要） | 否则 cc 或其他渠道拒绝 | 会话专题 §4.3 |
| 按“模型 × 渠道”声明去掉上游会拒绝的字段或 beta 值 | 避免上游 400 | §4.2 |
| `x-claude-code-*` 头不转发给上游 | 这些头供网关使用 | §4.2 |

上表之外的改写都需要单独论证，并加入此表。

## 2. CCR 与 dsh 对比，以及自研要解决的痛点

### 2.1 优缺点

| | CCR（v3.1.3+） | dsh（0.2.1-rc.3+） |
|---|---|---|
| 优点 | cc 和桌面版的入站兼容最完整（环境变量、apiKeyHelper、桌面 configLibrary、bootstrap 端点）；场景路由经过社区检验；有 key 池、额度连接器、托管 web search、视觉 MCP 等现成思路；预设覆盖国内主要 coding plan | 国产模型差异用声明式 compat 字段描述，粒度细；对 tool_use / tool_result 配对、thinking 签名、图片能力做严格校验，宁可报错也不静默修补；错误分类清晰；web 能力的分层设计干净；MIT |
| 缺点 | v3 把协议转换下沉到 `@the-next-ai/ai-gateway`，npm 上只有编译产物，**核心转换不可审阅**；功能面约 11.7 万行，远超个人网关需求；国产模型预设只到端点 / 协议层；token 估算是纯启发式；桌面端自动应用会切换生效配置，丢失用户 Default 的字段 | 不是入站网关，没有 `/v1/messages` 服务端；国产模型适配依赖 pi-ai；默认组合挂载会话日志扩展；整个 harness 很重，不适合整体搬用 |

### 2.2 自研要解决的痛点

1. **可审计、可控**：协议转换是网关最核心也最容易出错的部分，必须是自己能读、能测的代码。
2. **“静默成功”问题**：参数被丢弃却返回 200（thinking、cache_control、图片、工具字段）。网关每一处改写都要可观测。
3. **缓存命中**：用户的主要成本在长输入。网关不能破坏前缀稳定性，也要把各家缓存用量正确映射回 Anthropic 字段。
4. **会话中途换模型**：thinking 签名、工具 id、图片、上下文窗口在跨模型、跨渠道时都会出问题，见专题文档。
5. **桌面版的配置安全**：只生成配置片段，不自动覆盖；配置可备份、可回滚。
6. **多渠道额度**：统一查看各渠道的余额和 5h、周、月窗口（只读展示）。

## 3. 总体架构

```text
Claude 桌面端（Code 模式）/ Claude Code CLI（本人设备）
   │  HTTPS，Authorization: Bearer <网关签发的 key>
   ▼
https://<你的域名>
   │  TLS 终结：本机 nginx / Caddy，或另一台机器上的反代（到网关这一跳必须加密，§8.5）
   ▼
┌──────────────── claude-gateway @ 你的服务器（只监听 127.0.0.1） ──────────────────────┐
│ edge-guard  鉴权（常量时间比较，读请求体之前完成）、按 key/IP 限流、IP 白名单（可选）、  │
│             认证失败快速拒绝与记录、请求体上限                                         │
│ server      /v1/messages、/v1/messages/count_tokens、/v1/models、/health              │
│ resolver    对外 ID → 模型 × 渠道 × key（一一对应）；会话识别与切换检测                 │
│ protocol    anthropic 原生透传 + compat profile（OpenAI 转换器为备用）                 │
│ accounts    渠道 credential；额度窗口查询（只读展示）                                  │
│ enhance     （M4）图片转写等                                                         │
│ observability  基本请求日志（元数据、脱敏）、usage、诊断事件                            │
└──────────────────────────────────────────────────────────────────────────────────────┘
   │  出站：上游地址白名单、redirect=error、超时与取消
   ├─ deepseek        https://api.deepseek.com/anthropic            （按量）
   ├─ zhipu-api       https://open.bigmodel.cn/api/anthropic        （按量）
   ├─ zhipu-coding    https://open.bigmodel.cn/api/anthropic        （GLM Coding Plan，与上一行同一 URL）
   ├─ ark-coding      https://ark.cn-beijing.volces.com/api/coding  （方舟 Coding Plan）
   └─ ark-api         https://ark.cn-beijing.volces.com/api/compatible（方舟按量，供 M4 视觉转写等网关自发调用）
```

**请求流水线**（每一步都可以产生诊断事件）：

1. 边界防护：校验网关 key，失败时立即返回 401 并记录，不读请求体；之后做限流、IP 白名单和请求体上限检查。
2. 解析与归一：保留原始字节，只解析必要字段，不重排、不重新序列化（见 §4.6）。
3. 解析对外 ID：按配置得到唯一的“模型 × 渠道 × key”；用 `x-claude-code-session-id` 加 agent-id 识别会话线，检测用户是否切换了模型。不认识的 ID 返回 `not_found_error`。
4. 能力检查：对照目标“模型 × 渠道”的能力，处理 thinking、图片、server tool、cache_control 等。
5. 协议适配：原生透传加 compat profile。
6. 出站：选 credential，注入上游认证，**清除客户端认证头**，设置超时，绑定客户端断连取消。
7. 回流：SSE 原样转发；`message_start` 里的 `model` 回写为客户端请求的模型名。
8. 收尾：写基本请求日志（usage 含缓存、耗时、渠道、诊断），释放并发占用。

## 4. 对 Claude 桌面端与 Claude Code 的兼容

桌面端（Code 模式）在内部启动一个内置版本的 Claude Code，所以发给网关的请求协议与 CLI 相同。差异在于配置方式、模型 ID 检查、模型发现和窗口推断，详见[桌面端接入](桌面端接入.md)。

### 4.1 端点清单

| 端点 | MVP | 说明 |
|---|---|---|
| `POST /v1/messages` | ✅ | 流式和非流式都支持 |
| `POST /v1/messages/count_tokens` | ✅ | 策略见 §4.7 |
| `GET /v1/models` | ✅ | 桌面端：`?limit=1000`，可翻页（`after_id`），约 10s 超时，读取 `id`、`display_name`、`description`、`anthropic_family_tier`、`is_family_default`、`supports_1m`、`max_input_tokens`、`max_effort_level`（[桌面端接入 §3](桌面端接入.md#3-模型发现)）。CLI：需要 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`，3s 超时，只读 id / 名称 / 描述。**这个端点由网关直接应答，不重定向** |
| `GET /health` | ✅ | 不需要鉴权，只返回 `ok`，不暴露版本和配置 |
| cc 启动时的引导类请求 | M0 确认 | 只实现抓包中真实出现的端点，不伪造成功响应 |
| 其他路径 | 否 | 统一返回 404；需要鉴权的路径在鉴权失败时返回 401，不透露路径是否存在 |

### 4.2 Messages 字段兼容策略

总原则：**原生 Anthropic 上游默认透传；目标模型或渠道声明不支持时，按 profile 决定 strip / 改写 / 拒绝，并记录诊断；不允许静默丢弃。**

| 字段 / 内容 | 原生 Anthropic 上游（本期主路径） |
|---|---|
| `system`、`text` | 透传 |
| `image` 块 | 按“模型 × 渠道”能力判断：支持就透传，不支持就转写（M4）或拒绝（§7.3） |
| `document`、`search_result` 等 | 上游不支持时（例如 DeepSeek 官方文档列为 Not Supported）返回 400 并说明原因 |
| `tool_use` / `tool_result` | 透传；校验配对（借鉴 dsh，调研 §3.2）。`is_error` 被上游忽略时记诊断 |
| `thinking` / `redacted_thinking` | 按[专题 §4.2](会话管理与模型切换.md#42-跨模型的-thinking--reasoning_content)过滤；DeepSeek 官方不支持 `redacted_thinking` |
| `tools`、`tool_choice` | 透传；新字段（如 `defer_loading`）按 profile 处理 |
| server tools（`web_search_*` 等） | 上游声明支持时透传（DeepSeek 官方文档列 `server_tool_use` / `web_search_tool_result` 为 Supported），否则交给 §7 的增强或拒绝 |
| `thinking` 参数、`output_config.effort` | 按模型能力映射（§4.5）；DeepSeek 忽略 `budget_tokens`，只支持 `effort` |
| `cache_control` | 透传；上游忽略时（DeepSeek 官方文档列为 Ignored）记诊断，以 usage 判断实际是否命中 |
| `metadata.user_id` | 默认**不透传**（cc 的这个字段含 device_id / account_uuid，属于隐私）。DeepSeek 用它做限流隔离，是否透传一个网关生成的稳定匿名值由 profile 决定 |
| `max_tokens` | 按“模型 × 渠道”元数据截断并记诊断，**不写死数值** |
| `anthropic-beta` 请求头 | 国产端点按 profile 去掉已知会被拒绝的值，并记诊断；以后接 Anthropic 官方时原样透传（cc 网关协议文档的要求） |
| `x-claude-code-*` 请求头 | 网关自己使用，**不转发**给上游 |

### 4.3 流式 SSE

- 字节级转发；只在 `message_start` 里把 `model` 改回客户端请求的模型名（专题 Q-S8）。遵守背压，不缓冲整段响应。
- `ping` 保活：上游长时间不出字节时由网关发 `ping`，避免公网链路上的代理或客户端超时。
- 流中出错时发 Anthropic `error` 事件后结束，不伪造 `end_turn`。
- 客户端断连时立即取消上游请求，释放并发占用。
- 上游错误（包括首字节前的连接失败、429、5xx）原样返回客户端，网关不重试、不换渠道；只做 §1.2 登记过的措辞改写。
- 公网反代层（nginx / Caddy）必须关闭响应缓冲，并把读超时设得足够长（§8.5）。

### 4.4 tool_use / tool_result 细节

- 原生上游的 id 原样透传；用户切换模型后的 id 兼容见专题 §4.3。
- 校验配对：assistant 发出的每个 tool_use 都必须在下一条 user 消息里有对应的 tool_result。不满足时直接返回 400，并说明原因。

### 4.5 thinking / extended thinking

- cc 侧有三种情况：`thinking: {type: enabled, budget_tokens}`、`{type: adaptive}`、不带 thinking；另有 `output_config.effort`。按“模型 × 渠道”的能力映射，各渠道的实际行为在 M0 实测后写入 profile。
  - 已知：DeepSeek 官方 thinking “Supported（budget_tokens 被忽略）”，`output_config` 只支持 `effort`。
  - 方舟 Coding Plan 文档说明，GLM-5.3 和 Kimi-K3 默认开启思考且不支持关闭，DeepSeek V4 系列默认开启、可手动关闭。
  - cc 发出 `thinking: disabled`、但模型不支持关闭时，网关记诊断后照常转发，**不报错**。
- **签名与跨模型**：见[会话管理与模型切换](会话管理与模型切换.md)。
  - cc 在用户切换模型后会自行剥掉异源的签名 thinking。同一模型的不同渠道是不同的对外 ID，因此 cc 同样会剥。
  - cc 剥不到的部分（无签名的 thinking、目标渠道不支持的 redacted_thinking）由网关按登记表和渠道 profile 去掉。
  - 各渠道返回的 thinking 是否带签名、能否互认，在 M0 验证。

### 4.6 Prompt caching

- `cache_control` 透传；各渠道是否真的支持（DeepSeek 官方忽略该字段，走自动前缀缓存）由 profile 声明，以 usage 为准。
- **网关不能破坏前缀**：
  - 不在前部注入动态内容。
  - 不重排 tools 或 JSON 键。
  - 每个对外 ID 固定一个渠道和一把 key。
  - 图片转写结果按哈希缓存。
- **`usage` 原样返回**，包括 `cache_creation_input_tokens` 和 `cache_read_input_tokens`。桌面端和 cc 据此计算上下文用量；缺了缓存字段就会少算，导致超限之前不压缩（[桌面端接入 §4.4](桌面端接入.md#44-usage-与流式)）。
- **缓存按“渠道 × 账号 × 模型”隔离**：用户切换到另一个对外 ID 后，第一轮必然全量未命中，网关记录预估成本（专题 §4.6）。
- 验收标准：同一段长前缀连续请求时，比较直连和经过网关的上游 usage。

### 4.7 count_tokens

按以下顺序选择：

1. 上游有原生 `count_tokens` 并声明支持时，直接转发（**Coding Plan 渠道除外**，见 §6.3：网关不主动对 Coding Plan 渠道发起非交互调用）。
2. 有开源 tokenizer 的模型在本地计算。
3. 启发式估算，并用该模型最近的真实 `input_tokens` 校准系数。

cc 用这个结果判断上下文用量和压缩时机，所以**宁可偏大**。

### 4.8 模型名映射（模型 × 渠道）

桌面端要求模型 ID 呈 Claude 形态：ID 中出现 `deepseek`、`glm`、`kimi`、`doubao`、`seed-` 等片段的条目会被移出列表（[桌面端接入 §2.4](桌面端接入.md#24-模型-id-检查关键约束)）。因此对外 ID 与真实模型名分开：

- **对外 ID**：格式为 `claude-gw-<别名>`。**每个“模型 × 渠道”一个对外 ID**，一一对应，没有备用渠道。`display_name` 写成“真实模型（渠道）”，例如 `claude-gw-dsv4pro` 显示为“DeepSeek V4 Pro（官方）”，`claude-gw-dsv4pro-hs` 显示为“DeepSeek V4 Pro（火山）”。
- **别名校验**：网关加载配置时，按与桌面端相同的规则校验每个对外 ID（内置一份片段表，标注来源的桌面端版本）。不通过时拒绝启动，并给出原因。
- **Claude 真实 ID 作别名**（可选）：例如把 `claude-sonnet-4-6` 映射到某个国产模型。Claude Code 会按那个 Claude 模型的能力和窗口假设来处理，适合“让某个档位直接映射到国产模型”的场景。
- **档位**：配置中的 `clients.tiers` 为 haiku、sonnet、opus 各指定一个默认对外 ID。它们由 `/v1/models` 以 `anthropic_family_tier` / `is_family_default` 返回，并写入桌面端和 cc 的配置片段。这样档位别名、子 agent、后台小任务都能解析到指定的对外 ID（§4.9）。
- **上游模型 ID**：不同渠道的上游 ID 不同（方舟按量端点带版本后缀，例如 `doubao-seed-2-1-pro-260628`；方舟 Coding Plan 用短名，例如 `doubao-seed-2.1-pro`；DeepSeek 官方用 `deepseek-v4-pro`、`deepseek-flash`），由渠道配置中的 `upstreamModel` 映射承担。
- **回显**：`message.model` 回显对外 ID（会话专题 Q-S8）。
- **窗口声明同源**：对外 ID 的 `max_input_tokens` / `supports_1m`、桌面端条目的 `supports1m`，以及 cc settings 中按模型的压缩窗口，都由 `cgw` 从同一份“模型 × 渠道”元数据生成。

### 4.9 场景与模型的对应

网关按对外 ID 转发，不按场景（后台、长上下文、思考、子 agent）改模型。哪类请求用哪个对外 ID，由客户端的档位配置决定；网关负责生成这些配置片段，并让 `/v1/models` 返回档位信息。

| 请求 | 客户端如何选择模型（[桌面端接入 §2.5](桌面端接入.md#25-档位后台小任务与子-agent-用哪个模型)） | 配置方式 |
|---|---|---|
| 主会话 | 用户在桌面端选择器或 `/model` 中选择 | 桌面端 `inferenceModels`；CLI `ANTHROPIC_MODEL` |
| 后台小任务（标题、摘要等） | haiku 档 pin；没有 pin 时用主会话模型 | 桌面端：一个对外 ID 标 `anthropicFamilyTier: haiku`；CLI：`ANTHROPIC_DEFAULT_HAIKU_MODEL` |
| 内置 Explore / Plan 子 agent | 继承主会话模型 | — |
| 其他子 agent | agent 定义的 `model` → `CLAUDE_CODE_SUBAGENT_MODEL` → 主会话模型；档位别名解析到对应 pin | CLI：`CLAUDE_CODE_SUBAGENT_MODEL`；桌面端是否读取，待 M0 |
| opusplan | plan 阶段用 opus 档，执行阶段用 sonnet 档 | 桌面端 opus / sonnet 档条目；CLI `ANTHROPIC_DEFAULT_{OPUS,SONNET}_MODEL` |

- `cgw desktop print-config` 和 `cgw print-cc-settings` 为 haiku、sonnet、opus 三档各生成一个默认对外 ID，避免某个档位没有 pin、cc 退回 Claude 内置 ID。
- 请求中的模型不是已配置的对外 ID 时，网关返回 `not_found_error`，消息中写明请求的 ID，并提示配置对应档位。
- 上下文超限：上游错误已是 cc 能识别的措辞时原样转发；是已知的非 Anthropic 措辞时，改写为 `prompt is too long` 格式（§1.2），让 cc 自己压缩。
- 渠道失败或 Coding Plan 额度用完：原样返回错误，用户在客户端改选其他对外 ID。

### 4.10 Transformer 机制：借鉴与改进

| CCR 的做法 | 问题 | 本方案 |
|---|---|---|
| v2：transformer 四钩子，作用于 OpenAI 统一格式 | Anthropic 独有字段在转换中容易丢失；补丁写死 | 内部格式即 Anthropic；本期四个渠道都走原生透传，只应用 compat profile |
| v2：每家一个 transformer 类 | 差异散落，难以对比 | **声明式 compat profile**，按渠道和“模型 × 渠道”两级覆盖 |
| v3：协议核心在闭源编译包里 | 不可审阅 | 自己实现，每个 profile 字段都配 fixture 契约测试 |
| 改写没有可观测性 | 出现静默成功 | 每次改写产生 `Diagnostic{code, field, action, channel, model}`，写入请求日志 |

### 4.11 接入方式

**Claude 桌面端（Code 模式，第一接入对象）**：

- 在 **Developer → Configure Third-Party Inference…** 中把 provider 设为 Gateway，或使用 `cgw desktop print-config` 生成的配置片段：
  - `inferenceGatewayBaseUrl`：网关地址。
  - `inferenceCredentialKind: "static"` 加 `inferenceGatewayApiKey`（网关签发的 key），或使用 `helper-script`。
  - `inferenceModels`：对外 ID、显示名、`supports1m` / `prefer1m`、档位、`maxEffort`。
- 模型列表二选一：
  - 写显式完整 ID 列表（桌面端会自动跳过模型发现）；
  - 或打开发现，让桌面端读取网关的 `/v1/models`。
- 压缩窗口：桌面端启动的 Claude Code 不继承终端里的 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`。`cgw` 同时生成 Claude Code settings 片段（按模型的压缩窗口），见[桌面端接入 §4.2](桌面端接入.md#42-压缩窗口怎么设置)。
- 网关**不自动写**桌面配置，只提供 `print-config` 以及 `backup` / `restore`。

**Claude Code CLI**（写在 `~/.claude/settings.json` 的 `env` 中，或由 `cgw print-cc-settings` 生成）：

- `ANTHROPIC_BASE_URL=https://<你的域名>`。
- 认证二选一：
  - `ANTHROPIC_AUTH_TOKEN=<网关签发的 key>`（以 Bearer 发送）。
  - 用 `apiKeyHelper` 指向本机脚本，从系统钥匙串读取网关 key，key 就不需要明文写在 settings 里。**推荐 apiKeyHelper。**
- 模型：`ANTHROPIC_MODEL`、`ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`、`CLAUDE_CODE_SUBAGENT_MODEL`。
- 会话与窗口：
  - `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`。
  - `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`。
  - `CLAUDE_CODE_MAX_CONTEXT_TOKENS`，以及按模型的压缩窗口（专题 §4.5）。
- 流量：`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`。方舟文档说明遥测类请求默认会走 base URL 并占用 Coding Plan 额度；对网关来说，这也能减少无关流量。
- 超时：`API_TIMEOUT_MS`，按公网链路调大。
- 提供 `cgw cc [args]` 启动器：只给子进程注入环境变量，不修改全局 settings。

### 5.3 模型 × 渠道配置

```yaml
models:                             # 键为对外 ID：一个对外 ID = 一个“模型 × 渠道”
  claude-gw-dsv4pro:
    displayName: DeepSeek V4 Pro（官方）
    channel: deepseek
    upstreamModel: deepseek-v4-pro
    contextWindow: 1000000
  claude-gw-dsv4pro-hs:
    displayName: DeepSeek V4 Pro（火山）
    channel: ark-coding
    upstreamModel: deepseek-v4-pro
    contextWindow: 1000000
  claude-gw-zp53-plan:
    displayName: GLM-5.3（智谱套餐）
    channel: zhipu-coding
    upstreamModel: glm-5.3

clients:
  tiers:                            # 生成客户端档位配置，网关不据此改模型（§4.9）
    opus: claude-gw-dsv4pro
    sonnet: claude-gw-zp53-plan
    haiku: claude-gw-dsflash
```

- 对外 ID 在加载配置时按桌面端规则校验（§4.8）。
- 能力（`inputModalities`、`contextWindow`、`maxOutputTokens`、thinking 能否关闭）按对外 ID 声明，因为同一模型在不同渠道上的限制可能不同。
- compat profile 字段参照 pi-ai（调研 §3.3）：渠道一级写通用差异，对外 ID 一级写个例。

### 5.4 差异处理清单

- **错误映射**：上游错误统一映射为 Anthropic 错误类型。上下文超限统一改写为 cc 认得的 `prompt is too long` 文案；签名类错误改写为 cc 认得的文案（专题 §4.2）；Coding Plan 额度耗尽时，上游的状态码和错误体原样返回，网关只记诊断码。如果上游返回 `retry-after`，原样保留（cc 网关协议文档要求它是整数秒；超过 60 时 cc 停止自动重试，直接提示）。
- **thinking 不可关闭**：见 §4.5。
- **max_tokens**：按“模型 × 渠道”元数据截断。
- **遥测**：不发送任何网关自己的扩展字段或识别头；`x-claude-code-*` 头不转发。

## 7. 后续增强（M4 起）

### 7.1 搜索增强（web search）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 网关托管 | 拦截 `web_search_*` server tool，由网关执行搜索并按 Anthropic 结构注入结果（CCR hosted-web-search，调研 §2.5） | 对 cc 透明 | 流式拼接复杂 |
| B MCP 工具 | 提供 `cgw-search` MCP server，在 cc 里注册，并禁用内置 WebSearch | 实现简单，与网关解耦 | 需要配置 cc |
| C 渠道原生 | DeepSeek 官方支持 `server_tool_use` / `web_search_tool_result`；智谱 Coding Plan 自带联网搜索、网页读取 MCP（与模型共享套餐额度） | 不用自己维护 | 能力因渠道而异 |

**建议**：先做 C 的透传加 B。智谱的搜索 MCP 由 cc 直接连接，不经过网关，属于官方支持的用法。

### 7.2 网页抓取（web fetch）

- cc 的 WebFetch 由客户端抓取，再交给小模型处理。只要 haiku 档或主会话模型可用，它基本就能工作。
- 增强点放在 MCP（`cgw-fetch`）：可读性提取、SSRF 防护、大小和时长上限。

### 7.3 多模态增强（看图）

- **网关层转写（主方案）**：目标“模型 × 渠道”不支持图片时，调用视觉模型生成描述，替换为文本块；按 `sha256(图片) + 视觉模型 + 提示词版本` 缓存。
- **视觉模型**：豆包 Seed 2.1 pro / lite（方舟模型列表标注支持多模态理解）。**走 `ark-api` 按量渠道，不走 Coding Plan**，因为转写是网关自发的非交互调用（§6.3）。
- 转写失败时不能静默丢图（具体失败行为见 §11）。
- 方舟 Coding Plan 上的 GLM-5.3-Flash、Kimi-K3 等本身支持图片。用户选择这些模型时直接透传，不需要转写。

### 7.4 网关层还是 MCP

结论不变：**内联图片转写放在网关层，搜索和抓取先用 MCP**。

## 8. 技术栈、模块与部署

### 8.1 技术栈（已定）

- **Node.js 22+ / TypeScript（ESM）**：与 cc、CCR、dsh、pi-ai 同属一个生态。
- HTTP：原生 `node:http` 加轻量路由；出站用 undici（连接池、`redirect: 'error'`、AbortSignal）。
- 配置：YAML 加 zod 校验，支持热加载（失败时保留旧配置）。
- 存储：SQLite（better-sqlite3）只保存元数据，包括请求日志、usage、会话状态和网关 key 的哈希。
- 日志：pino 结构化日志，经过脱敏。
- 测试：vitest；录制的上游 fixture 加模拟上游做契约测试。

### 8.2 模块与目录

| 目录 | 职责 |
|---|---|
| `src/server/` | HTTP 入站、端点分发、SSE 输出 |
| `src/auth/` | 网关 key 校验、限流、IP 白名单、认证失败记录（边界防护） |

### 8.3 配置格式

完整示例见 [`config/gateway.example.yaml`](../config/gateway.example.yaml)。主要配置块：`server`、`security`（网关 key、限流、IP 白名单）、`channels`（端点、计费类型、credential 引用、compat）、`models`（键为对外 ID，每个对应一个“模型 × 渠道”，含档位与窗口声明）、`clients`（生成桌面端和 cc 配置片段用的档位默认值）、`enhance`、`logging`。

### 8.4 安全设计（第一优先级）

**访问控制**：

- **网关 key**：
  - 由 `cgw key create` 生成，格式为 `cgw_` 前缀加 32 字节随机数（base62）。
  - 服务器上只保存其 SHA-256 哈希和元数据（名称、创建时间、过期时间、允许的模型）。明文只在创建时显示一次。
  - 支持吊销和轮换；建议设置过期时间。
- cc 用 `ANTHROPIC_AUTH_TOKEN`（`Authorization: Bearer`）或 `apiKeyHelper` 携带 key；网关同时接受 `x-api-key`，因为 cc 可能两个头都发。
- **鉴权在读取请求体之前完成**，比较使用常量时间。失败时立即返回 401，响应体固定，不区分“key 不存在”和“key 已吊销”。
- **认证失败记录与封禁**：记录来源 IP、时间、key 前缀（只记前 8 位）和路径。同一 IP 短时间内多次失败就临时封禁（指数退避），封禁事件写入审计日志。
- **限流**：
  - 按 key：rpm 和并发上限。
  - 按 IP：未认证请求的速率上限。
  - 请求体大小上限（cc 请求可能很大，默认 32MB，可调）。
- **可选 IP 白名单**：支持 CIDR。开启后，不在名单内的请求在鉴权之前直接拒绝。
- **只暴露必要端点**：没有任何管理端点监听在公网上。管理通过服务器上的 `cgw` CLI 进行（SSH 登录后执行）。

**传输**：

- **强制 HTTPS**：网关进程只监听 `127.0.0.1`，TLS 在边缘终结（§8.5）。如果边缘与网关不在同一台机器上（§8.5 经反代），中间这一跳也必须加密（TLS 加 mTLS，或 WireGuard），不允许在公网上明文转发。
- 公网 80 端口只做跳转，或者干脆不开放。cc 的 base URL 一律写 https。
- TLS 1.2 及以上；开启 HSTS。

**上游密钥**：

- 只保存在服务器上：放在 `0600` 权限的环境文件或 systemd credentials 中，配置文件只引用变量名。
- 出站前清除客户端的 `authorization` / `x-api-key`，再注入渠道 key。
- 上游地址固定白名单，`redirect: 'error'`。

**日志与数据**：

- 基本请求日志只记元数据：时间、请求 ID、会话 ID、request-class、请求的模型、实际“模型 × 渠道”、状态码、耗时、usage（含缓存）、诊断码。
- **不记录正文，不记录任何密钥**。认证头和 key 一律掩码。
- 日志按天轮转，默认保留 14 天。

**运行**：

- 网关以专用低权限用户运行，由 systemd 守护（`NoNewPrivileges`、`ProtectSystem` 等加固项）。
- 依赖版本锁定；服务器只开放公网入口端口和 SSH，并且 SSH 先完成加固（§8.5 主机加固清单）。暴露在公网的云服务器普遍面临持续的 SSH 爆破，主机层面的加固与网关自身的鉴权同等重要。

**被入侵时的影响面**：

- 网关 key 泄露：可以吊销，影响限于调用额度。
- 服务器被入侵：上游 key 会暴露。因此各渠道 key 尽量使用该平台支持的最小权限和用量上限。

### 8.5 部署

目标环境是一台国内云服务器（Linux，Node.js 22+）。建议使用包年包月实例，并在控制台确认实例、系统盘和公网带宽的计费方式（固定带宽还是按流量）。仓库和公开文档里不要写真实的公网 IP、实例 ID 和域名，真实值只放在本地配置中。

国内云服务器通常无法直连 `api.anthropic.com`，这不影响本期（本期只接国产渠道）。

**公网入口（二选一）**

- **本机 TLS**：网关所在机器上的 nginx / Caddy 直接对外提供 TLS。
  - 在中国大陆，服务器的 80/443 通常要求域名已在**该云厂商**完成接入备案，否则会被拦截。上线前请确认域名的备案状态，或改用其他已备案域名。
  - 证书可用 acme.sh 或 certbot，以 DNS-01 验证签发（不依赖 80 端口）。
- **经反代**：TLS 在另一台机器（例如已有备案的服务器）上终结，再转发到网关机器。
  - 反代到网关这一跳**必须加密**：网关流量里有对话正文和网关 key，不允许在公网上明文转发。可用 TLS 加 mTLS（客户端证书），或 WireGuard 隧道，再叠加源地址放行（安全组加主机防火墙）。
  - 网关只在 `trustProxyHeaders` 开启、且请求来自 `trustedProxies` 时，才采信 `X-Forwarded-For` 中的真实客户端 IP。限流和认证失败封禁都基于这个 IP。
  - 代价是多一跳延迟、多一个故障点。
- 两种方式共同的要求：
  - 反代层关闭响应缓冲（nginx 为 `proxy_buffering off`），读超时不低于 10 分钟，保留 `Authorization` 头，开启 HTTP/2。
  - 网关进程只监听 `127.0.0.1`。
  - 机器上已有的其他反代配置或防火墙规则，不要与网关混用同一路径或端口。

**上线前主机加固清单**（M1 前置条件，上线公网网关之前完成）：

1. **SSH**：
   - 只允许密钥登录（`PasswordAuthentication no`）。
   - `PermitRootLogin` 设为 `no` 或 `prohibit-password`，日常使用普通用户加 sudo。
   - 安全组把 22 端口的来源限制为固定 IP；做不到时安装 fail2ban。
   - 改完之后，用新会话验证可以登录，再断开旧会话。
2. **入站最小化**：安全组和主机防火墙（ufw 或 iptables 二选一，不要混用造成规则冲突）只放行 SSH 和公网入口端口。经反代时，网关端口只放行反代来源。
3. **journald**：设置 `SystemMaxUse`，防止日志占满磁盘；网关自己的日志按 §8.4 轮转。
4. **清理**：部署前检查并清理不再使用的服务、端口和旧配置。
5. 网关运行用户、systemd 加固项按 §8.4 执行。

**资源**：2 核 / 4G 左右对单人使用的 Node 网关加 SQLite 足够。M4 的图片转写调用外部视觉模型，不在本机跑模型。

## 12. 边界

以下内容不在本项目当前范围内，集中列在这里。

- **使用者**：单部署、单使用者。不做多租户、多用户、计费或转售；不做多 key 轮询来突破单账号限额（Coding Plan 条款普遍禁止拆分账号、共享凭证、请求聚合，§6.3）。
- **干预**：不做提示词优化，不由网关主动压缩上下文，不改写 cc 的提示词或工具集来“教模型调用工具”（CCR v2 `tooluse` 那类做法，调研 §2.1）；只做 §1.2 列出的必要改写。
- **模型与渠道的选择**：不做自动渠道切换或失败回退（含首字节前的重试换渠道、Coding Plan 额度用完时切到按量渠道、额度快用完时提前切走）；不由网关自行更换模型、渠道或 key；不做多 key 池自动轮转（也就不会引起跨账号切换）；一个对外 ID 不设备用渠道链。
- **场景路由**：不做 CCR 式的按场景（后台、长上下文、思考、webSearch、图片）改模型的路由，也不做路由规则或脚本。场景与模型的对应由客户端档位配置决定（§4.9）。
- **缓存**：不做语义缓存或响应缓存（它和供应商的 prompt KV 缓存是两回事，§4.6）。
- **客户端**：不支持桌面端的 Chat、Cowork 模式；不接管 Codex、OpenCode 等其他 agent；不做 Electron 桌面壳。
- **上游**：Claude Pro/Max 订阅直通和 Anthropic 官方 API key 不在本期范围。以后如果做，只考虑“本人直通、不保存、不池化、不伪造客户端身份”；国内服务器通常无法直连 `api.anthropic.com`，需要海外出口。
- **验证**：不做防掺水 / 可信验证（例如校验上游是否真的是所声明的模型）。本期只保留排障用的基本请求日志（元数据，不含正文）。
- **转换**：OpenAI 格式转换为备用（M3），本期不实现。
- **形态**：本期不提供本机一键体验（`npx` / Docker）和管理 UI。
