# claude-gateway 方案 v0.1

日期：2026-10-27。状态：**M1 实现中**：M0 渠道实测结果见 [M0 渠道行为实测](M0-渠道行为.md)。已定事项见 §0.1；开放设计问题见 §11。

源码证据和版本锁定见[参考项目源码调研](research/参考项目源码调研.md)，下文“调研 §x”均指该文档。会话与模型切换的专题设计见[会话管理与模型切换](会话管理与模型切换.md)。

设计前比较过 CCR 仅网关模式、LiteLLM、NewAPI / Bifrost 等现有方案。在“数据和密钥自控、协议转换可审计”优先的前提下，本项目选择自建一层独立的 Messages 薄转发层，本方案是它的扩展版设计。

## 0. 一页结论

- **定位**：一个人自己部署，让 **Claude 桌面端（Code 模式）** 和 Claude Code 顺畅使用国产模型的网关。单部署、单使用者；部署在自己的服务器上，通过公网 HTTPS 访问。
- **第一接入对象是桌面端 Code 模式**，CLI 版 Claude Code（cc）同时支持。桌面端的约束（模型 ID 形态、模型发现、窗口推断）见[桌面端接入](桌面端接入.md)。
- **纯透传**：网关默认不改请求和响应，只做必要的兼容改写，每处改写都记录诊断（§1.2）。
- **优先保证服务器部署**。
- **安全是第一优先级**：
  - 网关自己签发访问 key，上游真实 key 只放在服务器上。
  - 强制 HTTPS，认证失败快速拒绝并记录。
  - 按 key 和 IP 限流，IP 白名单可选，日志脱敏（§8.4）。
- **本期重点**是“与 cc 的兼容”和“与模型的交互”：协议保真、国产模型差异、会话与模型切换、缓存。
- **首批上游**为四个渠道：DeepSeek 官方、智谱 GLM 普通 API、智谱 GLM Coding Plan、火山方舟 Coding Plan。**四家都有原生 Anthropic 兼容端点**（§5.2），所以本期主路径全部是原生透传加 compat profile，OpenAI 格式转换（原 M3）降为备用。
- **模型 × 渠道，显式选择**：同一个模型可能有多条渠道，例如 DeepSeek V4 Pro 既可以走官方，也可以走火山方舟 Coding Plan。每个“模型 × 渠道”配一个对外 ID，在桌面端分别列出；一个对外 ID 固定对应一个“模型 × 渠道”。用哪个由用户在客户端选择（§4.8、§5.3）。
- **内部格式选 Anthropic Messages**；差异处理借鉴 dsh / pi-ai 的声明式 compat profile；每一处改写都记录诊断，不做静默丢弃。
- **场景与模型的对应由客户端的档位配置决定**：后台小任务、子 agent、opusplan 分别用哪个对外 ID，由桌面端的 tier 和 cc 的 `ANTHROPIC_DEFAULT_*_MODEL` 决定；网关生成这些配置片段（§4.9）。
- **错误原样返回**：上游失败（含 Coding Plan 额度用完）时，网关把错误返回给客户端，只做已登记的措辞兼容改写（§1.2）。
- **Coding Plan**：各家 Coding Plan 对使用范围有限制，使用者需自行阅读并遵守官方条款；本项目不提供、也不鼓励转售、共享或池化（§6.3）。
- **技术栈**：Node.js 22+ / TypeScript / undici（已定）。
- 本期范围之外的内容集中列在 §12“边界”。

## 1. 定位、目标与原则

### 1.1 目标

1. Claude 桌面端（Code 模式）和 cc 通过一个公网 HTTPS 地址，按会话或场景使用首批四个渠道的模型。桌面端是第一接入对象。
2. 协议层兼容要可审计：代码自己掌握，转换规则可读，有回归用例。
3. 对话正文和上游密钥由部署者自己掌控：网关跑在部署者自己的服务器上，上游 key 只留在服务器上。
4. 公网暴露下的安全：只有持有网关 key 的部署者本人客户端能调用，攻击面最小。
5. 会话与模型切换行为正确，缓存保持命中，长会话能正常自动压缩。

### 1.2 纯透传原则

网关默认**原样转发**请求和响应（字节级，包括 `usage`、SSE 事件、错误体），只做下列**必要的兼容改写**。每一处改写都产生一条诊断，写入请求日志：

| 改写 | 原因 | 细节 |
|---|---|---|
| 认证头替换 | 客户端持有的是网关 key，要换成上游 key | §3、§8.4 |
| 模型名映射，以及 `message.model` 回显对外 ID | 桌面端要求 Claude 形态的模型 ID；cc 按 `message.model` 判断是否换了模型 | §4.8、[桌面端接入 §6](桌面端接入.md#6-对网关设计的影响) |
| 已知的非 Anthropic 超长错误改写为 cc 能识别的措辞 | 否则 cc 不触发压缩，会话卡死 | [桌面端接入 §4.3](桌面端接入.md#43-超长错误典型问题与网关的必要改写) |
| 上游错误按「状态码 + 错误码 / type + 原文」组合分类，按类别调整给客户端的信号：余额或额度耗尽套用已确认文案（包含上游原文）、设 `error.type: billing_error` 并加 `x-should-retry: false`；认证失败、模型不可用、参数错误加 `x-should-retry: false`；限流和过载在上游没给 `retry-after` 时按规则补上。其余情况报错原文不改。未命中规则的错误原样透传 | 同一个状态码可能是完全不同的错误（例如智谱的 429 既可能是余额不足 1113，也可能是限流 1302）；cc 对 429 会静默重试多次，余额不足时用户要等很久才看到原因 | §5.4 |
| 签名类错误改写为 cc 能识别的措辞；用户切换模型后，按目标渠道的 `thinkingReplay` 去掉无法接受的 thinking 块，并去掉保留下来的 thinking 块上的 `cache_control` | cc 只剥带签名的异源块，其余块可能让目标渠道报错；DeepSeek 等渠道又要求无签名 thinking 原样回传 | 会话专题 §4.2 |
| 用户切换模型后，上游因历史不兼容返回的回放类 400 改写为带建议的错误（文案已确认，见会话专题 §4.8） | 原始错误让用户看不出该怎么办；改写后的措辞不得命中 cc / 桌面端会自动处理的触发词 | 会话专题 §4.8 |
| 在 system 末尾追加静态的并发说明（用户明确要求的例外；配置了 `concurrency` 的对外 ID 默认开启，可关闭） | 让模型起子任务时控制并发；内容对每个“模型 × 渠道”固定，不破坏缓存 | §4.12 |
| 上游 tool_use id 不符合 Anthropic 格式时做可逆编码（如 M0 证实需要） | 否则 cc 或其他渠道拒绝 | 会话专题 §4.3 |
| 按“模型 × 渠道”声明去掉上游会拒绝的字段或 beta 值 | 避免上游 400 | §4.2 |
| `x-claude-code-*` 头不转发给上游 | 这些头供网关使用 | §4.2 |

上表之外的改写都需要单独论证，并加入此表。

## 2. CCR 与 dsh 对比，以及自研要解决的痛点

### 2.1 优缺点

| | CCR（v3.1.3+） | dsh（0.2.1-rc.3+） |
|---|---|---|
| 优点 | cc 和桌面版的入站兼容最完整（环境变量、apiKeyHelper、桌面 configLibrary、bootstrap 端点）；场景路由经过社区检验；有 key 池、额度连接器、托管 web search、视觉 MCP 等现成思路；预设覆盖国内主要 coding plan | 国产模型差异用声明式 compat 字段描述，粒度细；对 tool_use / tool_result 配对、thinking 签名、图片能力做严格校验，宁可报错也不静默修补；错误分类清晰；web 能力的分层设计干净；MIT |
| 缺点 | v3 把协议转换下沉到 `@the-next-ai/ai-gateway`，npm 上只有编译产物，**核心转换不可审阅**；功能面约 11.7 万行，远超个人网关需求；国产模型预设只到端点 / 协议层；token 估算是纯启发式；桌面端自动应用会切换生效配置，丢失用户 Default 的字段 | 不是入站网关，没有 `/v1/messages` 服务端；国产模型适配依赖 pi-ai；默认组合挂载会话日志扩展；整个 harness 很重，不适合整体搬用 |

### 2.2 自研要解决的痛点

1. **可审计、可控**：协议转换是网关最核心也最容易出错的部分，必须是自己能读、能测的代码。
2. **“静默成功”问题**：参数被丢弃却返回 200（thinking、cache_control、图片、工具字段）。网关每一处改写都要可观测。
3. **缓存命中**：用户的主要成本在长输入。网关不能破坏前缀稳定性，也要把各家缓存用量正确映射回 Anthropic 字段。
4. **会话中途换模型**：thinking 签名、工具 id、图片、上下文窗口在跨模型、跨渠道时都会出问题，见专题文档。
5. **桌面版的配置安全**：只生成配置片段，不自动覆盖；配置可备份、可回滚。
6. **多渠道额度**：统一查看各渠道的余额和 5h、周、月窗口（只读展示）。

## 3. 总体架构

```text
Claude 桌面端（Code 模式）/ Claude Code CLI（本人设备）
   │  HTTPS，Authorization: Bearer <网关签发的 key>
   ▼
https://<你的域名>
   │  TLS 终结：本机 nginx / Caddy；或经反代机，反代再以 HTTPS（证书固定、可选双向 TLS）转发到网关（§8.5）
   ▼
┌──────────────── claude-gateway @ 你的服务器（只监听 127.0.0.1） ──────────────────────┐
│ edge-guard  鉴权（常量时间比较，读请求体之前完成）、按 key/IP 限流、IP 白名单（可选）、  │
│             认证失败快速拒绝与记录、请求体上限                                         │
│ server      /v1/messages、/v1/messages/count_tokens、/v1/models、/health              │
│ resolver    对外 ID → 模型 × 渠道 × key（一一对应）；会话识别与切换检测                 │
│ protocol    anthropic 原生透传 + compat profile（OpenAI 转换器为备用）                 │
│ accounts    渠道 credential；额度窗口查询（只读展示）                                  │
│ enhance     （M4）图片转写等                                                         │
│ observability  基本请求日志（元数据、脱敏）、usage、诊断事件                            │
└──────────────────────────────────────────────────────────────────────────────────────┘
   │  出站：上游地址白名单、redirect=error、超时与取消
   ├─ deepseek        https://api.deepseek.com/anthropic            （按量）
   ├─ zhipu-api       https://open.bigmodel.cn/api/anthropic        （按量）
   ├─ zhipu-coding    https://open.bigmodel.cn/api/anthropic        （GLM Coding Plan，与上一行同一 URL）
   ├─ ark-coding      https://ark.cn-beijing.volces.com/api/coding  （方舟 Coding Plan）
   └─ ark-api         https://ark.cn-beijing.volces.com/api/compatible（方舟按量，供 M4 视觉转写等网关自发调用）
```

**请求流水线**（每一步都可以产生诊断事件）：

1. 边界防护：校验网关 key，失败时立即返回 401 并记录，不读请求体；之后做限流、IP 白名单和请求体上限检查。
2. 解析与归一：保留原始字节，只解析必要字段，不重排、不重新序列化（见 §4.6）。
3. 解析对外 ID：按配置得到唯一的“模型 × 渠道 × key”；用 `x-claude-code-session-id` 加 agent-id 识别会话线，检测用户是否切换了模型。不认识的 ID 返回 `not_found_error`。
4. 能力检查：对照目标“模型 × 渠道”的能力，处理 thinking、图片、server tool、cache_control 等。
5. 协议适配：原生透传加 compat profile。
6. 出站：选 credential，注入上游认证，**清除客户端认证头**，设置超时，绑定客户端断连取消。
7. 回流：SSE 原样转发；`message_start` 里的 `model` 回写为客户端请求的模型名。
8. 收尾：写基本请求日志（usage 含缓存、耗时、渠道、诊断），释放并发占用。

## 4. 对 Claude 桌面端与 Claude Code 的兼容

桌面端（Code 模式）在内部启动一个内置版本的 Claude Code，所以发给网关的请求协议与 CLI 相同。差异在于配置方式、模型 ID 检查、模型发现和窗口推断，详见[桌面端接入](桌面端接入.md)。

### 4.1 端点清单

| 端点 | MVP | 说明 |
|---|---|---|
| `POST /v1/messages` | ✅ | 流式和非流式都支持 |
| `POST /v1/messages/count_tokens` | ✅ | 策略见 §4.7 |
| `GET /v1/models` | ✅ | 桌面端：`?limit=1000`，可翻页（`after_id`），约 10s 超时，读取 `id`、`display_name`、`description`、`anthropic_family_tier`、`is_family_default`、`supports_1m`、`max_input_tokens`、`max_effort_level`（[桌面端接入 §3](桌面端接入.md#3-模型发现)）。CLI：需要 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`，3s 超时，只读 id / 名称 / 描述。**这个端点由网关直接应答，不重定向** |
| `GET /health` | ✅ | 不需要鉴权，只返回 `ok`，不暴露版本和配置 |
| cc 启动时的引导类请求 | M0 确认 | 只实现抓包中真实出现的端点，不伪造成功响应 |
| 其他路径 | 否 | 统一返回 404；需要鉴权的路径在鉴权失败时返回 401，不透露路径是否存在 |

### 4.2 Messages 字段兼容策略

总原则：**原生 Anthropic 上游默认透传；目标模型或渠道声明不支持时，按 profile 决定 strip / 改写 / 拒绝，并记录诊断；不允许静默丢弃。**

| 字段 / 内容 | 原生 Anthropic 上游（本期主路径） |
|---|---|
| `system`、`text` | 透传 |
| `image` 块 | 原样透传。目标“模型 × 渠道”不支持图片时，由上游返回错误，网关原样转发（默认主模型 DeepSeek V4.1 Flash 支持图片） |
| `document`、`search_result` 等 | 上游不支持时（例如 DeepSeek 官方文档列为 Not Supported）返回 400 并说明原因 |
| `tool_use` / `tool_result` | 透传；校验配对（借鉴 dsh，调研 §3.2）。`is_error` 被上游忽略时记诊断 |
| `thinking` / `redacted_thinking` | 按[专题 §4.2](会话管理与模型切换.md#42-跨模型的-thinking--reasoning_content)过滤；DeepSeek 官方不支持 `redacted_thinking` |
| `tools`、`tool_choice` | 透传；新字段（如 `defer_loading`）按 profile 处理 |
| server tools（`web_search_*` 等） | 上游声明支持时透传（DeepSeek 官方文档列 `server_tool_use` / `web_search_tool_result` 为 Supported），否则交给 §7 的增强或拒绝 |
| `thinking` 参数、`output_config.effort` | 按模型能力映射（§4.5）；DeepSeek 忽略 `budget_tokens`，只支持 `effort` |
| `cache_control` | 透传；上游忽略时（DeepSeek 官方文档列为 Ignored）记诊断，以 usage 判断实际是否命中 |
| `metadata.user_id` | 默认**不透传**（cc 的这个字段含 device_id / account_uuid，属于隐私）。DeepSeek 用它做限流隔离，是否透传一个网关生成的稳定匿名值由 profile 决定 |
| `max_tokens` | 按“模型 × 渠道”元数据截断并记诊断，**不写死数值** |
| `anthropic-beta` 请求头 | 国产端点按 profile 去掉已知会被拒绝的值，并记诊断；以后接 Anthropic 官方时原样透传（cc 网关协议文档的要求） |
| `x-claude-code-*` 请求头 | 网关自己使用，**不转发**给上游 |

### 4.3 流式 SSE

- 字节级转发；只在 `message_start` 里把 `model` 改回客户端请求的模型名（专题 Q-S8）。遵守背压，不缓冲整段响应。
- `ping` 保活：上游长时间不出字节时由网关发 `ping`，避免公网链路上的代理或客户端超时。
- 流中出错时发 Anthropic `error` 事件后结束，不伪造 `end_turn`。
- 客户端断连时立即取消上游请求，释放并发占用。释放操作**幂等**，放在 `finally` 中：客户端断连和上游结束同时发生时，只释放一次。
- **超时分三种**，按渠道配置（profile 的 `timeouts`）：
  - **连接超时**：默认较短，例如 10s。
  - **首字节超时**：默认放宽到 600s。大上下文下首 token 可能超过 120s，期间网关发 `ping` 保活。
  - **空闲超时**：流开始后两次数据之间的最长间隔。
- **并发上限**：按“模型 × 渠道”配置（渠道上设默认，对外 ID 上可覆盖），计数单位是同时处理中的请求（从发出到响应结束）。默认值依据各家官方说明（2026-10-27 查阅）：

  | 渠道 | 官方说明 | 网关默认值 |
  |---|---|---|
  | DeepSeek 官方 | 按账户限并发：`deepseek-flash` 2500、`deepseek-v4-pro` 500，超出返回 429（[Rate Limit](https://api-docs.deepseek.com/quick_start/rate_limit)） | 不限（单人用量远低于上限，留给上游 429） |
  | 智谱按量 API | 按账户“用户权益等级 × 模型”分别限并发，数值只在控制台“速率限制”页可见；超出返回错误码 1302（[速率限制](https://docs.bigmodel.cn/cn/api/rate-limit)、[用户权益](https://docs.bigmodel.cn/cn/guide/platform/equity-explain)） | 示例值 5，部署时按控制台填写 |
  | 智谱 Coding Plan | 按套餐等级统一并发、动态调整，低峰期更高，不支持申请调整；官方只给建议（Lite 单个项目、Pro 1–2 个、Max 2 个以上），未给数字（同上） | 2（保守值，可调） |
  | 火山方舟 Coding Plan | 文档正文未给出并发数，只说明 5 小时 / 周 / 月三级额度、“TPM 满足正常开发需求”（[套餐概览](https://ark.volcengine.com/region:cn-beijing/docs/coding-plan-personal-plan-overview)）。火山官网文章称 Lite 2 路、Pro 8 路，每 5 小时约 1200 / 6000 次请求，待控制台确认 | 2（按 Lite） |
  | 火山方舟按量 | 按 RPM / TPM 限流（模型列表中按模型给出） | 不限 |

  超限时：排队最多 60s，超时后返回带提示的 429（§4.12）。排队不改变请求内容，属于保护性限制。
- 上游错误（包括首字节前的连接失败、429、5xx）返回客户端，网关不重试、不换渠道；错误先按 §5.4 分类，只做 §1.2 登记过的改动。**过载类错误也不自动重试**（例如智谱的 1302 账户并发上限、1305 平台过载，方舟的 429），否则会和 cc 自带的重试叠加成重试风暴。分类结果写入诊断，区分“限流”和“过载”，并保留上游的 `retry-after`。
- 公网反代层（nginx / Caddy）必须关闭响应缓冲，并把读超时设得足够长（§8.5）。

### 4.4 tool_use / tool_result 细节

- 原生上游的 id 原样透传；用户切换模型后的 id 兼容见专题 §4.3。
- 校验配对：assistant 发出的每个 tool_use 都必须在下一条 user 消息里有对应的 tool_result。不满足时直接返回 400，并说明原因。

### 4.5 thinking / extended thinking

- cc 侧有三种情况：`thinking: {type: enabled, budget_tokens}`、`{type: adaptive}`、不带 thinking；另有 `output_config.effort`。按“模型 × 渠道”的能力映射，各渠道的实际行为在 M0 实测后写入 profile。
  - 已知：DeepSeek 官方 thinking “Supported（budget_tokens 被忽略）”，`output_config` 只支持 `effort`。
  - 方舟 Coding Plan 文档说明，GLM-5.3 和 Kimi-K3 默认开启思考且不支持关闭，DeepSeek V4 系列默认开启、可手动关闭。
  - cc 发出 `thinking: disabled`、但模型不支持关闭时，网关记诊断后照常转发，**不报错**。
- **签名与跨模型**：见[会话管理与模型切换](会话管理与模型切换.md)。
  - cc 在用户切换模型后会自行剥掉异源的签名 thinking。同一模型的不同渠道是不同的对外 ID，因此 cc 同样会剥。
  - cc 剥不到的部分（无签名的 thinking、目标渠道不支持的 redacted_thinking）由网关按登记表和渠道 profile 去掉。
  - 各渠道返回的 thinking 是否带签名、能否互认，在 M0 验证。

### 4.6 Prompt caching

- `cache_control` 透传；各渠道是否真的支持（DeepSeek 官方忽略该字段，走自动前缀缓存）由 profile 声明，以 usage 为准。
- **网关不能破坏前缀**：
  - 不在前部注入动态内容。
  - 不重排 tools 或 JSON 键。
  - 每个对外 ID 固定一个渠道和一把 key。
  - 图片转写结果按哈希缓存。
- **`usage` 原样返回**，包括 `cache_creation_input_tokens` 和 `cache_read_input_tokens`。桌面端和 cc 据此计算上下文用量；缺了缓存字段就会少算，导致超限之前不压缩（[桌面端接入 §4.4](桌面端接入.md#44-usage-与流式)）。
- **缓存按“渠道 × 账号 × 模型”隔离**：用户切换到另一个对外 ID 后，第一轮必然全量未命中，网关记录预估成本（专题 §4.6）。
- 验收标准：同一段长前缀连续请求时，比较直连和经过网关的上游 usage。

### 4.7 count_tokens

按以下顺序选择：

1. 上游有原生 `count_tokens` 并声明支持时，直接转发（**Coding Plan 渠道除外**，见 §6.3：网关不主动对 Coding Plan 渠道发起非交互调用）。
2. 有开源 tokenizer 的模型在本地计算。
3. 启发式估算，并用该模型最近的真实 `input_tokens` 校准系数。

cc 用这个结果判断上下文用量和压缩时机，所以**宁可偏大**。

### 4.8 模型名映射（模型 × 渠道）

桌面端要求模型 ID 呈 Claude 形态：ID 中出现 `deepseek`、`glm`、`kimi`、`doubao`、`seed-` 等片段的条目会被移出列表（[桌面端接入 §2.4](桌面端接入.md#24-模型-id-检查关键约束)）。因此对外 ID 与真实模型名分开：

- **对外 ID**：格式为 `claude-gw-<别名>`。**每个“模型 × 渠道”一个对外 ID**，一一对应，没有备用渠道。`display_name` 写成“真实模型（渠道）”，例如 `claude-gw-dsv4pro` 显示为“DeepSeek V4 Pro（官方）”，`claude-gw-dsv4pro-hs` 显示为“DeepSeek V4 Pro（火山）”。
- **别名校验**：网关加载配置时，按与桌面端相同的规则校验每个对外 ID（内置一份片段表，标注来源的桌面端版本）。不通过时拒绝启动，并给出原因。
- **Claude 真实 ID 作别名**（可选）：例如把 `claude-sonnet-4-6` 映射到某个国产模型。Claude Code 会按那个 Claude 模型的能力和窗口假设来处理，适合“让某个档位直接映射到国产模型”的场景。
- **档位**：配置中的 `clients.tiers` 为 haiku、sonnet、opus 各指定一个默认对外 ID。它们由 `/v1/models` 以 `anthropic_family_tier` / `is_family_default` 返回，并写入桌面端和 cc 的配置片段。这样档位别名、子 agent、后台小任务都能解析到指定的对外 ID（§4.9）。
- **上游模型 ID**：不同渠道的上游 ID 不同（方舟按量端点带版本后缀，例如 `doubao-seed-2-1-pro-260628`；方舟 Coding Plan 用短名，例如 `doubao-seed-2.1-pro`；DeepSeek 官方用 `deepseek-v4-pro`、`deepseek-flash`），由渠道配置中的 `upstreamModel` 映射承担。
- **回显**：`message.model` 回显对外 ID（会话专题 Q-S8）。
- **窗口声明同源**：对外 ID 的 `max_input_tokens` / `supports_1m`、桌面端条目的 `supports1m`，以及 cc settings 中按模型的压缩窗口，都由 `cgw` 从同一份“模型 × 渠道”元数据生成。

### 4.9 场景与模型的对应

网关按对外 ID 转发，不按场景（后台、长上下文、思考、子 agent）改模型。哪类请求用哪个对外 ID，由客户端的档位配置决定；网关负责生成这些配置片段，并让 `/v1/models` 返回档位信息。

| 请求 | 客户端如何选择模型（[桌面端接入 §2.5](桌面端接入.md#25-档位后台小任务与子-agent-用哪个模型)） | 配置方式 |
|---|---|---|
| 主会话 | 用户在桌面端选择器或 `/model` 中选择 | 桌面端 `inferenceModels`；CLI `ANTHROPIC_MODEL` |
| 后台小任务（标题、摘要等） | haiku 档 pin；没有 pin 时用主会话模型 | 桌面端：一个对外 ID 标 `anthropicFamilyTier: haiku`；CLI：`ANTHROPIC_DEFAULT_HAIKU_MODEL` |
| 内置 Explore / Plan 子 agent | 继承主会话模型 | — |
| 其他子 agent | agent 定义的 `model` → `CLAUDE_CODE_SUBAGENT_MODEL` → 主会话模型；档位别名解析到对应 pin | CLI：`CLAUDE_CODE_SUBAGENT_MODEL`；桌面端是否读取，待 M0 |
| opusplan | plan 阶段用 opus 档，执行阶段用 sonnet 档 | 桌面端 opus / sonnet 档条目；CLI `ANTHROPIC_DEFAULT_{OPUS,SONNET}_MODEL` |

- `cgw desktop print-config` 和 `cgw print-cc-settings` 按 `clients.tiers` 为 haiku、sonnet、opus 三档各生成一个对外 ID，避免某个档位没有 pin、cc 退回 Claude 内置 ID。默认值见 §0.1；使用者可以改，主对话仍可在桌面端随时切换。
- 同一个对外 ID 同时用于两个档位时（例如默认值中 sonnet 和 haiku 都是 DeepSeek V4.1 Flash）：
  - cc 的环境变量两个档位都指向它即可。
  - 桌面端的每个 `inferenceModels` 条目只能带一个档位，`name` 又不能重复，所以生成器为第二个档位自动生成一个指向同一“模型 × 渠道”的**档位别名 ID**，例如 `claude-gw-dsflash-haiku`。别名同样通过桌面端规则校验，网关按原 ID 转发。

  桌面端对这种写法的实际行为，[待 M0] 确认。
- 请求中的模型不是已配置的对外 ID 时，网关返回 `not_found_error`，消息中写明请求的 ID，并提示配置对应档位。
- 上下文超限：上游错误已是 cc 能识别的措辞时原样转发；是已知的非 Anthropic 措辞时，改写为 `prompt is too long` 格式（§1.2），让 cc 自己压缩。
- 渠道失败或 Coding Plan 额度用完：原样返回错误，用户在客户端改选其他对外 ID。

### 4.11 接入方式

**Claude 桌面端（Code 模式，第一接入对象）**：

- 在 **Developer → Configure Third-Party Inference…** 中把 provider 设为 Gateway，或使用 `cgw desktop print-config` 生成的配置片段：
  - `inferenceGatewayBaseUrl`：网关地址。
  - `inferenceCredentialKind: "static"` 加 `inferenceGatewayApiKey`（网关签发的 key），或使用 `helper-script`。
  - `inferenceModels`：对外 ID、显示名、`supports1m` / `prefer1m`、档位、`maxEffort`。
- 模型列表二选一：
  - 写显式完整 ID 列表（桌面端会自动跳过模型发现）；
  - 或打开发现，让桌面端读取网关的 `/v1/models`。
- 压缩窗口：桌面端启动的 Claude Code 不继承终端里的 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`。`cgw` 同时生成 Claude Code settings 片段（按模型的压缩窗口），见[桌面端接入 §4.2](桌面端接入.md#42-压缩窗口怎么设置)。
- 网关**不自动写**桌面配置，只提供 `print-config` 以及 `backup` / `restore`。

**Claude Code CLI**（写在 `~/.claude/settings.json` 的 `env` 中，或由 `cgw print-cc-settings` 生成）：

- `ANTHROPIC_BASE_URL=https://<你的域名>`。
- 认证二选一：
  - `ANTHROPIC_AUTH_TOKEN=<网关签发的 key>`（以 Bearer 发送）。
  - 用 `apiKeyHelper` 指向本机脚本，从系统钥匙串读取网关 key，key 就不需要明文写在 settings 里。**推荐 apiKeyHelper。**
- 模型：`ANTHROPIC_MODEL`、`ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`、`CLAUDE_CODE_SUBAGENT_MODEL`。
- 会话与窗口：
  - `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`。
  - `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`。
  - `CLAUDE_CODE_MAX_CONTEXT_TOKENS`，以及按模型的压缩窗口（专题 §4.5）。
- 流量：`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`。方舟文档说明遥测类请求默认会走 base URL 并占用 Coding Plan 额度；对网关来说，这也能减少无关流量。
- 超时：`API_TIMEOUT_MS`，按公网链路调大。
- 提供 `cgw cc [args]` 启动器：只给子进程注入环境变量，不修改全局 settings。

### 4.12 并发：超限报错、告诉模型、观测

**超限时的行为**（2026-10-27 定）：

- 先**排队**，最多 60s。
- 超时后返回错误，并明确告诉用户：这是并发上限问题，可以切换到其他模型。
- 排队期间不改变请求内容。

**为什么返回 429，并带 `retry-after: 120`**：

- cc 对 429 默认会**静默自动重试**，最多 `CLAUDE_CODE_MAX_RETRIES` 次（默认 10），重试期间只显示倒计时。如果直接返回普通 429，用户要等很多轮排队和重试之后才能看到错误（[errors：Automatic retries](https://code.claude.com/docs/en/errors)）。
- cc 网关协议文档写明：`retry-after` **大于 60** 时，cc 停止重试，**立即**显示错误（[llm-gateway-protocol：Response headers](https://code.claude.com/docs/en/llm-gateway-protocol)）。
- cc 2.1.311 显示 429 时，取 JSON 错误体的 `error.message`，拼成 `API Error: Request rejected (429) · <message>`，所以网关的提示文字会原样出现在 `·` 之后。
  - 只有错误体为空时，才使用 cc 自己的 `this may be a temporary capacity issue…`。
  - HTML 错误页时，使用页面标题。
- 桌面端会把这类文本归为普通 API 错误，不替换文字。前提是不命中它的固定分类关键词：`Rate limit reached`、`hit your limit`、`spend / weekly / monthly / daily / session limit`、`usage limit is set to`、`temporarily limiting requests`、`prompt is too long`、`Request too large` 等（[桌面端接入 §4.5](桌面端接入.md#45-桌面端如何处理-api-错误)）。
- 因此网关返回：
  - HTTP 429，`type: rate_limit_error`；
  - `retry-after: 120`；
  - `message` 为提示文案，诊断码 `cgw_concurrency_limit`。
- **提示文案**（2026-10-27 用户确认，原文不改；`{模型显示名}` 为对外 ID 的显示名，`{N}` 为其并发上限）：

  > 「{模型显示名}」当前同时进行中的请求已达上限（{N} 个，包括主对话和子任务），本次请求排队 60 秒后仍未轮到，已取消。可以稍后重发，或在模型选择器中切换到其他模型继续。（诊断码 cgw_concurrency_limit）

**告诉模型，让它控制子任务并发**：

1. **客户端原生上限（优先）**：
   - cc 用 `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY`（默认 10）限制同一轮里并行执行的“并发安全”工具调用数（2.1.311 代码）。
   - 启动子 agent 的 Agent 工具是“并发安全”的，所以同一轮里**并行启动的子 agent 数**也受这个值限制。
   - `cgw print-cc-settings` 和 `cgw desktop print-config` 把它写进 settings 的 `env`：取用户常用的“模型 × 渠道”并发上限减 1（为主对话留 1 个位置）。
   - 这个值不在官方 env-vars 文档里，属于未公开的设置；它也会限制并行的只读工具。桌面端内置的 cc 是否读取用户 settings 的 `env`，[待 M0]。
2. **系统提示词注入（可选，用户明确要求的透传例外）**：
   - 网关按目标“模型 × 渠道”在 system 中追加一段**静态**说明，写明该渠道的并发上限和“分批起子任务”的要求。内容只取自配置，不含实时数字。
   - **放置位置**：
     - cc 的 system 依次为归因块、身份块、主提示等，其中带 `cache_control` 断点。
     - 注入文本作为**最后一个** system 文本块追加，**不带** `cache_control`。cc 的 system 原样保留，前面已有的断点不受影响。
     - 因为内容对每个“模型 × 渠道”固定不变，后续请求的前缀与第一次一致，缓存可以命中。
     - system 是字符串时，确定性地转为两个文本块。
   - 只对主对话和子 agent 请求注入（判断依据：请求带工具定义，或 request-class 为 `main` / `subagent`），后台小任务不注入。
   - 每次注入都在请求日志中记一条改写诊断（§1.2）。
   - **默认值**（2026-10-27 定）：配置了 `concurrency` 的对外 ID 默认开启注入，未配置的不注入；可在配置中关闭。
   - **注入文本**（2026-10-27 用户确认，原文不改；`{N}` 为该对外 ID 配置的并发上限，`{N-1}` 由它算出，都是静态值）：

     > [claude-gateway] 你当前使用的模型渠道同时最多处理 {N} 个请求（主对话与所有子 agent 合计）。并行启动子 agent 或批量并行调用工具时，请让同时运行的子 agent 不超过 {N-1} 个；任务较多时分批进行，等前一批完成后再启动下一批。超出上限的请求会排队，排队超过 60 秒会失败。

3. **CLAUDE.md**：另一种原生做法，是在用户级 CLAUDE.md 中写一段固定说明（由 `cgw` 生成，列出各对外 ID 的上限）。但它对所有模型都一样，模型也不一定知道自己走的是哪个渠道，精度不如第 2 种。

**观测**：

| 做法 | 说明 | 评价 |
|---|---|---|
| 标准限流响应头 | Anthropic 使用 `anthropic-ratelimit-requests-*` / `tokens-*` 与 `retry-after`；OpenAI 使用 `x-ratelimit-*`；IETF 草案 [RateLimit header fields](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/)（`RateLimit-Policy`、`RateLimit`，第 11 版，2026-05） | cc 2.1.311 **不用**这些头来节流：它只在重试时读 `retry-after`，只为 claude.ai 套餐用量显示和 429 归类读 `anthropic-ratelimit-unified-*`。网关不应伪造 `anthropic-ratelimit-unified-*`，否则会被 cc 误判为套餐限额 |
| MCP 工具 `gateway_status` | 返回各“模型 × 渠道”当前在途数 / 上限 / 排队数 | 模型可以主动查询，但实时数字变化快，查询本身也占一轮工具调用 |
| `cgw status` CLI | 给人看的实时在途数 / 排队数 / 额度 | 用于排障 |

**推荐**：

- 网关在每个响应上附加 IETF 草案的 `RateLimit-Policy` / `RateLimit` 头（以当前对外 ID 的并发为配额）。成本低、属于标准做法，不改变响应体。
- 提供 `cgw status` CLI。
- 节流主要依靠第 1、2 种（客户端硬上限加静态说明）。
- `gateway_status` MCP 工具本期不做（2026-10-27 定，§12）。

  claude-gw-dsflash:
    displayName: DeepSeek V4.1 Flash（官方）

  claude-gw-zp53flash-plan:

- 对外 ID 在加载配置时按桌面端规则校验（§4.8）。
- 能力（`inputModalities`、`contextWindow`、`maxOutputTokens`、thinking 能否关闭）按对外 ID 声明，因为同一模型在不同渠道上的限制可能不同。

| 字段 | 取值 | 用途 |
|---|---|---|
| `authHeader` | `x-api-key` / `bearer` | 上游要求的认证头；有的 Anthropic 兼容端点只认 `Authorization: Bearer` |
| `betaStrip` | 字符串列表 | 上游会拒绝的 `anthropic-beta` 值。例如有的端点拒收 `fine-grained-tool-streaming-2025-05-14`、`context-1m-2025-08-07`；各渠道的实际值以 M0 为准 |
| `thinkingReplay` | `keep-unsigned` / `strip-foreign` / `passthrough` | 用户切换模型后历史 thinking 的处理（会话专题 §4.2） |
| `redactedThinking` | `supported` / `unsupported` | 是否接受 `redacted_thinking` |
| `timeouts` | `connectMs`、`firstByteMs`、`idleMs` | §4.3 |
| `concurrency` | 正整数或 `null`（不限） | 该渠道同时处理中的请求上限，可在对外 ID 上覆盖；默认值见 §4.3 |

### 5.4 差异处理清单

- **错误分类**（2026-10-28 用户要求：不能只靠状态码，要同时用码和内容判断）：
  - 判定依据是**组合条件**：HTTP 状态码、响应体里的错误码（`error.code` 或顶层 `code`）或 `error.type`、报错原文的正则。一条规则里除状态码外至少要有一项，因为同一个状态码在不同渠道、甚至同一渠道里代表不同的错误：智谱的 HTTP 429 有余额不足（1113）、套餐 5 小时上限（1308）、限流（1302）、过载（1305）等；方舟的 `QuotaExceeded` 一个错误码按原文又分为套餐额度用完、免费额度用完、排队任务数超限。
  - 规则是声明式数据，放在随代码发布的 [`config/error-rules.yaml`](../config/error-rules.yaml)，按服务商分成规则集（`common`、`deepseek`、`zhipu`、`ark`）。渠道 profile 用 `errorRuleSets` 引用规则集，用 `errorRules` 写本渠道追加的规则；匹配顺序为 `errorRules` → 引用的规则集 → `common`，先命中先用。加载配置时校验规则（类别、正则、`retryAfterSec` 范围等），不合法时拒绝启动。每条规则写明依据（实测样本或官方错误码文档）。
  - 类别：`quota_exhausted`（余额或额度耗尽）、`rate_limited`（限流）、`overloaded`（上游过载）、`context_overflow`（上下文超长）、`auth_failed`（认证失败）、`model_unavailable`（模型不存在或不在套餐内）、`history_incompatible`（切换后历史不兼容）、`signature_invalid`（thinking 签名无效）、`invalid_request`（参数错误）。没有命中任何规则的为 `unknown`，**原样透传**（状态码、错误体、响应头都不动）。
  - 按类别给客户端的响应。依据是 cc 2.1.311 的重试判定：cc 对 408、409、429、5xx 会重试，但响应头 `x-should-retry: false` 时不重试；`retry-after` 不超过 60 秒时按它等待后重试，超过 60 秒时不再重试；显示 429 时取 `error.message` 原文。

    | 类别 | 给客户端的响应 | cc 的表现 |
    |---|---|---|
    | `quota_exhausted` | 状态码不变；`error.message` 套用下面的已确认文案（其中包含上游原文）；`error.type` 设为 `billing_error`（cc 网关协议文档对“额度已达上限”的约定）；加 `x-should-retry: false` | 不重试，立即显示该文案 |
    | `auth_failed`、`model_unavailable`、`invalid_request` | 状态码与错误体不变；加 `x-should-retry: false` | 不重试（例如智谱 1311“套餐未开放该模型”的状态码是 429，否则会被重试） |
    | `rate_limited`、`overloaded` | 状态码与错误体不变；上游没给 `retry-after` 时按规则的 `retryAfterSec` 补上 | 等待后重试 |
    | `context_overflow` | cc 已能识别的措辞原样转发；否则改写为 `prompt is too long: <请求> tokens > <上限> maximum`（原文没有数字时为 `prompt is too long`） | 触发被动压缩 |
    | `history_incompatible` | 用户切换模型后改写为已确认的建议文案（会话专题 §4.8）；没有切换时原样转发 | 显示建议 |
    | `signature_invalid` | 改写为 cc 能识别的签名错误措辞 | 剥掉 thinking 后重试 |

  - **余额或额度耗尽的报错文案**（2026-10-28 用户确认，原文不改；`{模型显示名}` 为对外 ID 的显示名，`{上游原文}` 为上游 `error.message` 原样；配置字段 `quotaAdvice.messageTemplate`，诊断码 `cgw_quota_exhausted`）：

    > 「{模型显示名}」渠道返回余额或额度不足：{上游原文}。可以处理后重发，或在模型选择器中切换到其他模型继续。（诊断码 cgw_quota_exhausted）

  - 每次分类都在请求日志里记一条诊断（类别、命中规则、上游状态码、错误码与 type，不含报错正文）；`cgw status` 按渠道、类别、状态码汇总最近 24 小时的上游错误。
  - 如果上游返回 `retry-after`，原样保留（cc 网关协议文档要求它是整数秒）。
- **thinking 不可关闭**：见 §4.5。
- **max_tokens**：按“模型 × 渠道”元数据截断。
- **遥测**：不发送任何网关自己的扩展字段或识别头；`x-claude-code-*` 头不转发。

## 7. 后续增强（M4 起）

### 7.1 搜索（MCP，模型自主选择）

**为什么需要**：

- cc 的 WebSearch 依赖服务端执行的 `web_search` server tool。
- 首批四个渠道里，只有 **DeepSeek 官方**明确支持：
  - 它的 Anthropic 兼容表把 `server_tool_use` / `web_search_tool_result` 列为 Supported（[Anthropic API](https://api-docs.deepseek.com/guides/anthropic_api)）；
  - 它的 2026-10-17 公告提到，Claude Code 经服务端工具发起的 Search & Fetch 调用已经支持（[公告](https://api-docs.deepseek.com/news/news261017)）。
- 智谱和方舟的 Anthropic 兼容文档没有声明支持，[待 M0]。
- 因此选用其他渠道的模型时，需要一个独立的搜索工具。DeepSeek 官方的原生搜索照常透传。

**做法**：

- 采用作者自己的开源实现 [unified-web-search](https://github.com/naive-white-expert/unified-web-search)（MIT，2026-10-27 查阅的最新 commit 为 `bc1de3b`），移植为仓库附带的 MCP server `cgw-search`。
- MCP 是独立进程，不在网关的请求路径上，网关保持纯透传。
- **由模型自主选择参数**：深度、地域、结果数、时间范围、站点都作为工具参数交给模型决定；路由规则写在工具描述里，供模型参考。

**路由**（沿用 unified-web-search v2.1 的“少次数优先”）：

| 深度 | 调用次数 | 国内 | 海外 |
|---|---|---|---|
| `quick` | 1 | 火山联网搜索 | Tavily |
| `normal` | 1 | 火山联网搜索 | Tavily |
| `deep` | 不超过 2 | 火山联网搜索 + 第二源（百炼等） | Tavily + 第二源（百炼等） |

- 只调用配置了 key 的后端。指定国内平台（小红书、微信公众号等）时不调用 Tavily。
- **搜索后端的多 key**（2026-10-27 定，沿用 unified-web-search 的实现）：
  - Tavily 可配主 key 和备用 key：主 key 当月额度用完（401 / 429 / 432 / 433）后改用备用 key；主 key 额度用完时，海外查询把智谱提到第一位。
  - 腾讯 WSA 可配多把 key，遇到 401 / 429 时换下一把。
  - 这只适用于 MCP 的**搜索后端** key。模型渠道仍是“一个渠道一把 key、不做自动切换”（§6.2、§12）。
  - 使用多 key 时，请自行确认各搜索服务商的条款。
- 主路由全部失败，或成功但结果为空时，按优先级再尝试最多 2 个备用后端。
- **百炼的特点**：百炼联网搜索返回的是**模型生成的答案**，来源列表常为空，并且会产生模型 token 费用。所以它只用在 `deep` 的第二源，返回时单独标为“生成答案”，与检索结果分开。
- 智谱 Web Search API 可以作为可选后端，使用按量 key，不使用 Coding Plan key。它的 query 有长度上限，截断时在返回中注明。
- Tavily：从国内服务器访问的连通性待测。

**工具参数**：

| 参数 | 取值 | 说明 |
|---|---|---|
| `query` | 字符串 | 必填 |
| `intensity` | `quick` / `normal` / `deep` | 默认 `normal` |
| `region` | `auto` / `domestic` / `overseas` | 默认 `auto`：按查询词和站点判断。上游实现只有自动判断，这里新增显式参数，交给模型选择 |
| `max_results` | 1–20 | 默认 5 |
| `freshness` | 7 / 30 / 180 / 365（天） | 相对时间窗口 |
| `start_date` / `end_date` | `YYYY-MM-DD` | 精确日期窗口 |
| `sites` / `exclude_sites` | 域名列表 | 站点白名单 / 黑名单 |
| `platforms` | `xiaohongshu`、`wechat`、`weibo`、`zhihu`、`bilibili`、`douyin`、`gov`、`arxiv` | 展开为站点 |
| `topic` | `general` / `news` / `finance` | 仅 Tavily 生效 |

后端不支持的参数先放宽检索，再在本地后处理，并在返回里注明。

**返回**：

- `sources[]`：标题、URL、摘要、发布时间、站点。
- `generated_answer`：仅在用到百炼等生成型后端时出现，并注明来源后端。
- `provider`、`region_effective`、`params_applied`、`fallback_used`、`notes`。

**工具描述草稿**（给模型看，供实现时使用）：

> 联网搜索。根据问题自行决定参数：
> - `intensity`：简单事实、天气、价格用 `quick`；一般新闻、常识用 `normal`；研究、对比、需要多来源交叉验证时用 `deep`（会多调用一个来源，较慢、较贵）。
> - `region`：中文或国内站点、国内平台用 `domestic`；英文或海外话题用 `overseas`；拿不准用 `auto`。
> - 路由：国内 → 火山联网搜索；海外 → Tavily；`deep` 时再叠加一个来源（例如百炼）。百炼返回的是生成的答案而不是检索结果，会单独放在 `generated_answer` 中，使用前请用 `sources` 中的链接核对。
> - 需要时间范围时，优先用 `start_date` / `end_date`，其次用 `freshness`。需要限定来源时用 `sites` 或 `platforms`。
> - 结果为空时，可以换 `region`、放宽时间或改写关键词后再搜。

**其他**：

- 搜索 key、模型 key 分开声明：火山联网搜索 key、方舟模型 key、Agent Plan key 互不通用。
- 调用只记元数据，不记录查询内容以外的正文。

### 7.2 网页抓取（MCP，模型自主选择）

- cc 的 WebFetch 由客户端抓取，再交给小模型处理。只要 haiku 档或主会话模型可用，它基本就能工作。
- 增强做成仓库附带的 MCP（`cgw-fetch`），同样由模型选择参数：

  | 参数 | 取值 | 说明 |
  |---|---|---|
  | `url` / `urls` | 一个或多个 URL | 必填 |
  | `backend` | `auto` / `linkreader` / `direct` | `auto`：静态页先直连抓取，失败或疑似 SPA 空壳时改用方舟 LinkReader（按量 key） |
  | `max_chars` | 默认 50000 | 超出时截断，并标注 `truncated: true` |
  | `timeout` | 15–120 秒，默认 60 | — |

- **返回原文**（Markdown），不做 LLM 摘要，由 cc 自己处理长文本。
- 安全：SSRF 防护（禁止内网地址、逐跳校验重定向），以及大小和时长上限。
- 工具描述（给模型看）写明：适合 SPA 页面、中文站点和需要原文细节的场景；静态英文页用 cc 自带的 WebFetch 即可。

### 7.3 图片转写（后续参考设计，本期不做）

本期不做（§12）：大部分模型的图片能力已经够用，默认主模型也支持图片；目标模型不支持图片时，原样透传，由上游报错。以下设计保留作为将来参考。


- **作用范围**：只在目标“模型 × 渠道”不支持图片时生效。默认主模型 DeepSeek V4.1 Flash 本身支持图片，直接透传；用户切到不支持图片的模型时才转写。方舟 Coding Plan 上的 GLM-5.3-Flash、Kimi-K3 等也支持图片。
- **视觉模型**：豆包 Seed 2.1 pro / lite（方舟模型列表标注支持多模态理解）。**走 `ark-api` 按量渠道，不走 Coding Plan**，因为转写是网关自发的非交互调用（§6.3）。
- **确定性**：
  - 视觉调用使用 `temperature: 0`，关闭 thinking（避免推理型模型只输出思维链、正文为空），`max_tokens` 固定。
  - **正文为空视为失败**。
- **缓存**：
  - SQLite 持久化，键为 `sha256(原始字节) + 视觉模型 + 提示词版本 + 压缩参数版本`；过期时间不短于会话状态 TTL。
  - **失败结果不缓存**。
- **失败处理**：
  - 只有**本轮新出现**的图片转写失败时才报错（`onFailure: error`）。
  - 历史图片的缓存缺失时（例如被清理）重新转写；重试仍失败才报错。避免一次瞬时故障让整个会话卡死。
  - 失败信息不进入模型上下文。
- **压缩**：
  - 只压缩**发给视觉模型的副本**。透传给原生视觉渠道的 `image` 块保持原样。
  - 参数参考上游 Hermes Agent 的公开实现（[vision_tools.py#L315-L342](https://github.com/NousResearch/hermes-agent/blob/a72bb03757c0c925c686f9774eefc8dc5a77b329/tools/vision_tools.py#L315-L342)、[#L372-L517](https://github.com/NousResearch/hermes-agent/blob/a72bb03757c0c925c686f9774eefc8dc5a77b329/tools/vision_tools.py#L372-L517)）：目标 4MB，长边上限 7900px，JPEG 质量依次 85 → 70 → 50，每轮长边减半，最多 5 轮。
  - 按文件头魔数判断 MIME（[image_routing.py#L364-L396](https://github.com/NousResearch/hermes-agent/blob/a72bb03757c0c925c686f9774eefc8dc5a77b329/agent/image_routing.py#L364-L396)）。
- **并行与延迟**：
  - 多张图并行转写（设并发上限），单图超时约 60s。
  - 转写在上游请求之前完成，期间客户端收不到字节。能否在 `message_start` 之前发 `ping`，[待 M0]。
- **转写提示词和包装文字**：待用户确认，确认前不写入代码或文档。包装中不含时间戳等动态内容，并进入缓存键的版本号。
- **配置项**：`enhance.vision.promptVersion`、`maxImageBytes`、`maxImagesPerRequest`、`timeoutMs`、`concurrency`、`cacheTtlDays`。

### 7.4 网关层还是 MCP

搜索和抓取做成 MCP，网关保持纯透传。图片转写如果将来要做，只能放在网关层：粘贴的图片内联在请求里，模型没有机会自己调用工具（§7.3）。

## 8. 技术栈、模块与部署

### 8.1 技术栈（已定）

- **Node.js 22+ / TypeScript（ESM）**：与 cc、CCR、dsh、pi-ai 同属一个生态。

### 8.4 安全设计（第一优先级）

**访问控制**：

- **网关 key**：
  - 由 `cgw key create` 生成，格式为 `cgw_` 前缀加 32 字节随机数（base62）。
  - 服务器上只保存其 SHA-256 哈希和元数据（名称、创建时间、过期时间、允许的模型）。明文只在创建时显示一次。
  - 支持吊销和轮换；建议设置过期时间。
- cc 用 `ANTHROPIC_AUTH_TOKEN`（`Authorization: Bearer`）或 `apiKeyHelper` 携带 key；网关同时接受 `x-api-key`，因为 cc 可能两个头都发。
- **鉴权在读取请求体之前完成**，比较使用常量时间。失败时立即返回 401，响应体固定，不区分“key 不存在”和“key 已吊销”。
- **认证失败记录与封禁**：记录来源 IP、时间、key 前缀（只记前 8 位）和路径。同一 IP 短时间内多次失败就临时封禁（指数退避），封禁事件写入审计日志。
- **限流**：
  - 按 key：rpm 和并发上限。
  - 按 IP：未认证请求的速率上限。
  - 请求体大小上限（cc 请求可能很大，默认 64MB，可调；与反代的 `client_max_body_size` 保持一致）。
- **可选 IP 白名单**：支持 CIDR。开启后，不在名单内的请求在鉴权之前直接拒绝。
- **只暴露必要端点**：没有任何管理端点监听在公网上。管理通过服务器上的 `cgw` CLI 进行（SSH 登录后执行）。

**传输**：

- **强制 HTTPS**：本机 TLS 时，网关进程只监听 `127.0.0.1`，TLS 在本机 nginx / Caddy 终结。经反代时，反代到网关这一跳用 HTTPS + 证书固定 + 来源 IP 白名单，可选双向 TLS（推荐开启）。不允许在公网上明文转发（§8.5）。
- 公网 80 端口只做跳转，或者干脆不开放。cc 的 base URL 一律写 https。
- TLS 1.2 及以上；开启 HSTS。

**上游密钥**：

- 只保存在服务器上：放在 `0600` 权限的环境文件或 systemd credentials 中，配置文件只引用变量名。
- 出站前清除客户端的 `authorization` / `x-api-key`，再注入渠道 key。
- 上游地址固定白名单，`redirect: 'error'`。

**日志与数据**：

- 基本请求日志只记元数据：时间、请求 ID、会话 ID、request-class、请求的模型、实际“模型 × 渠道”、状态码、耗时、usage（含缓存）、诊断码。
- **不记录正文，不记录任何密钥**。认证头和 key 一律掩码。
- 日志按天轮转，默认保留 14 天。

**运行**：

- 网关以专用低权限用户运行，由 systemd 守护（`NoNewPrivileges`、`ProtectSystem` 等加固项）。
- 依赖版本锁定；服务器只开放公网入口端口和 SSH，并且 SSH 先完成加固（§8.5 主机加固清单）。暴露在公网的云服务器普遍面临持续的 SSH 爆破，主机层面的加固与网关自身的鉴权同等重要。

**被入侵时的影响面**：

- 网关 key 泄露：可以吊销，影响限于调用额度。
- 服务器被入侵：上游 key 会暴露。因此各渠道 key 尽量使用该平台支持的最小权限和用量上限。

### 8.5 部署

目标环境是一台国内云服务器（Linux，Node.js 22+）。建议使用包年包月实例，并在控制台确认实例、系统盘和公网带宽的计费方式（固定带宽还是按流量）。仓库和公开文档里不要写真实的公网 IP、实例 ID 和域名，真实值只放在本地配置中。

国内云服务器通常无法直连 `api.anthropic.com`，这不影响本期（本期只接国产渠道）。

**公网入口（二选一）**

- **本机 TLS**：网关所在机器上的 nginx / Caddy 直接对外提供 TLS，网关进程只监听 `127.0.0.1`。
  - 在中国大陆，服务器的 80/443 通常要求域名已在**该云厂商**完成接入备案，否则会被拦截。上线前请确认域名的备案状态，或改用其他已备案域名。
  - 证书可用 acme.sh 或 certbot，以 DNS-01 验证签发（不依赖 80 端口）。
- **经反代**：客户端访问已备案域名所在的反代机，反代机再通过公网 HTTPS 转发到网关机。适用于网关机所在云上没有可用备案域名的情况。
  - **客户端 → 反代机**：反代机 nginx 用公信证书对外提供 HTTPS。
  - **反代机 → 网关机**：这一跳用 **HTTPS + 证书固定 + 来源 IP 白名单，可选双向 TLS**（推荐开启）。
    - **网关直接监听 HTTPS 非标准端口**（例如 8443），使用**自签发的长期证书**：建一个小 CA 签发服务端证书，或直接自签。
      - 不用公信证书：网关机上的域名如果没有在该云接入备案，80/443 会被拦截；而且这一跳只有反代机一个调用方，固定证书比公信证书更严格，也省去 90 天续期。
      - 证书的 SAN 写一个固定名称（例如 `gateway.internal`），供反代机校验。
    - **证书固定**：反代机 nginx 设置 `proxy_ssl_verify on`，并用 `proxy_ssl_trusted_certificate` 指向该 CA（或该自签证书）；`proxy_ssl_name` 与证书 SAN 一致；`proxy_ssl_server_name on`。
    - **双向 TLS**（推荐）：反代机用 `proxy_ssl_certificate` / `proxy_ssl_certificate_key` 出示客户端证书，网关只接受带有该 CA 签发的客户端证书的连接，握手失败直接断开。
    - **来源 IP 白名单**：网关机的安全组（以及主机防火墙）只允许反代机的 IP 访问该端口。
    - 网关仍然校验自己签发的访问 key（§8.4）；双向 TLS 和 IP 白名单是额外的防线，不替代 key。
  - **真实客户端 IP**：网关只在 `trustProxyHeaders` 开启、且连接来自 `trustedProxies`（只填反代机）时，才采信 `X-Forwarded-For`。限流和认证失败封禁都基于这个 IP。
  - **带宽**：每一轮请求都携带完整的对话历史，请求体会经反代机的公网出口再转发一次。反代机如果是小的固定带宽，会成为明显瓶颈：按 1 token 约 4 字节估算，20 万 token 的请求体约 0.8MB，1M token 约 4MB，图片会更大。建议反代机的出口带宽不低于 5–10 Mbps，或改用按流量计费。
  - 代价是多一跳延迟、多一个故障点。
  - 通用配置示例见 [`deploy/nginx-reverse-proxy.example.conf`](../deploy/nginx-reverse-proxy.example.conf)。
- **两种方式共同的流式要求**（反代层）：
  - `proxy_buffering off`，不缓冲响应，保证 SSE 和 `ping` 逐条到达。
  - `proxy_request_buffering`：默认开启（nginx 先收完请求体再转发，网关拿到完整请求后才开始计时），也可以关闭以减少一次落盘。按实际效果选择，在 M1 部署时评估。
  - `proxy_read_timeout` 与网关的首字节超时对齐，不低于 600s；`proxy_send_timeout` 同样放宽。
  - `client_max_body_size` 足够大（例如 64m）：1M 上下文的请求体可达数 MB，含图片时更大。
  - 到上游用 HTTP/1.1 和 keepalive（`proxy_http_version 1.1`，清空 `Connection` 头），保留 `Authorization` 头。
  - 机器上已有的其他反代配置或防火墙规则，不要与网关混用同一路径或端口。

**上线前主机加固清单**（M1 前置条件，上线公网网关之前完成）：

1. **SSH**：
   - 只允许密钥登录（`PasswordAuthentication no`）。
   - `PermitRootLogin` 设为 `no` 或 `prohibit-password`，日常使用普通用户加 sudo。
   - 安全组把 22 端口的来源限制为固定 IP；做不到时安装 fail2ban。
   - 改完之后，用新会话验证可以登录，再断开旧会话。
2. **入站最小化**：安全组和主机防火墙（ufw 或 iptables 二选一，不要混用造成规则冲突）只放行 SSH 和公网入口端口。经反代时，网关端口只放行反代来源。
3. **journald**：设置 `SystemMaxUse`，防止日志占满磁盘；网关自己的日志按 §8.4 轮转。
4. **清理**：部署前检查并清理不再使用的服务、端口和旧配置。
5. 网关运行用户、systemd 加固项按 §8.4 执行。

**资源**：2 核 / 4G 左右对单人使用的 Node 网关加 SQLite 足够。M4 的图片转写调用外部视觉模型，不在本机跑模型。

## 10. 主要风险

| 风险 | 应对 |
|---|---|
| 使用 Coding Plan 渠道不符合服务商条款 | 使用者自行阅读并遵守条款（§6.3）；Coding Plan 渠道可单独停用，改用按量渠道 |
| 公网暴露后被扫描或暴力尝试 | §8.4：鉴权先于读请求体、失败封禁、限流、可选 IP 白名单、无公网管理端点；§8.5 主机加固清单 |
| cc 或桌面版升级后协议细节变化 | fixture 加契约测试；未知字段默认透传；每次升级跑回归清单 |
| 各家 Anthropic 兼容端点不完整或悄悄变化 | profile 诊断统计；定期探测；必要时启用备用的 OpenAI 转换 |
| 缓存命中被网关破坏 | §4.6 的约束加直连对比验收 |
| 经反代时中间一跳被窃听或冒充 | 这一跳用 HTTPS + 证书固定 + 来源 IP 白名单，推荐开启双向 TLS；网关仍校验访问 key |
| 反代机出口带宽小，长上下文请求转发慢 | 反代机出口带宽不低于 5–10 Mbps，或改用按流量计费（§8.5） |

## 12. 边界

以下内容不在本项目当前范围内，集中列在这里。

- **使用者**：单部署、单使用者。不做多租户、多用户、计费或转售；模型渠道不做多 key 轮询来突破单账号限额（Coding Plan 条款普遍禁止拆分账号、共享凭证、请求聚合，§6.3）。
- **干预**：不做提示词优化，不由网关主动压缩上下文，不改写 cc 的提示词或工具集来“教模型调用工具”（CCR v2 `tooluse` 那类做法，调研 §2.1）；只做 §1.2 列出的必要改写。
- **模型与渠道的选择**：不做自动渠道切换或失败回退（含首字节前的重试换渠道、Coding Plan 额度用完时切到按量渠道、额度快用完时提前切走）；不由网关自行更换模型、渠道或 key；不做多 key 池自动轮转（也就不会引起跨账号切换）；一个对外 ID 不设备用渠道链。
- **场景路由**：不做 CCR 式的按场景（后台、长上下文、思考、webSearch、图片）改模型的路由，也不做路由规则或脚本。场景与模型的对应由客户端档位配置决定（§4.9）。
- **缓存**：不做语义缓存或响应缓存（它和供应商的 prompt KV 缓存是两回事，§4.6）。
- **客户端**：不支持桌面端的 Chat、Cowork 模式；不接管 Codex、OpenCode 等其他 agent；不做 Electron 桌面壳。
- **上游**：Claude Pro/Max 订阅直通和 Anthropic 官方 API key 不在本期范围。以后如果做，只考虑“本人直通、不保存、不池化、不伪造客户端身份”；国内服务器通常无法直连 `api.anthropic.com`，需要海外出口。
- **验证**：不做防掺水 / 可信验证（例如校验上游是否真的是所声明的模型）。本期只保留排障用的基本请求日志（元数据，不含正文）。
- **重试**：网关不自动重试上游错误，包括过载类错误（§4.3）。
- **上游错误**：不为上游错误新增说明文字，报错原文只来自上游或已确认的文案；未命中分类规则的错误不做任何改动；不伪造 `anthropic-ratelimit-unified-*` 头。
- **图片**：本期不做图片转写（§7.3 的设计保留作为将来参考）；网关不压缩、不改写图片，目标模型不支持图片时由上游报错。
- **搜索与抓取**：网页抓取不做 LLM 摘要；搜索和抓取不进网关请求路径。
- **转换**：OpenAI 格式转换为备用（M3），本期不实现。
- **形态**：本期不提供本机一键体验（`npx` / Docker）和管理 UI。
- **观测**：本期不提供给模型查询实时并发的 `gateway_status` MCP 工具（§4.12）；实时状态通过响应头和 `cgw status` 查看。
