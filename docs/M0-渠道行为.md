- 探测脚本：`scripts/m0/probe.mjs`（上游 key 只从环境变量读取，输出只含状态码、白名单响应头、错误体和结构摘要）。
- CLI 抓包：`scripts/m0/capture-proxy.mjs`（本机记录型反代，认证头掩码，默认不保存正文）。
- 脱敏样本：`test/fixtures/deepseek/`、`test/fixtures/zhipu-coding/`（消息 id、request_id、签名已替换为全零），契约测试直接使用。

### 2.1 对 thinking 回放设计的修正

原设计（会话专题 §4.2）把 DeepSeek 定为 `keep-unsigned`：去掉带签名的块、保留无签名的块。实测 DeepSeek 自己的 thinking 也带签名，并且它接受任何来源的 thinking、又要求当前轮的工具调用必须带 thinking。所以对 DeepSeek 而言，删除只会制造 400，不会避免 400。DeepSeek 的 profile 改为 `passthrough`（只去掉它不支持的 `redacted_thinking`）。

cc 在用户切换模型后会剥掉异源消息上带签名的 thinking（会话专题 §2.1）。DeepSeek 的块带签名，所以：

- 从 DeepSeek 切到其他模型，cc 会剥掉 DeepSeek 的 thinking，目标渠道按自己的 profile 处理。
- 从其他模型切到 DeepSeek 时，只要切换发生在两次用户提问之间就能继续。切换发生在工具调用循环中间时（例如 opusplan 在 ExitPlanMode 之后从 opus 档切到 sonnet 档），DeepSeek 返回 must be passed back，网关改写为已确认的“历史不兼容”建议（`cgw_history_incompatible`）。

## 3. 智谱 Coding Plan

端点 `https://open.bigmodel.cn/api/anthropic`，模型 `glm-5.3-flash`，使用 Coding Plan 专用 key。Coding Plan 条款限定在官方支持的编程工具中交互式使用，所以只跑了判定 profile 必需的用例，`max_tokens` 尽量小；限流和超长两类需要大量或超大请求才能触发的用例没有跑。

| 项目 | 实测结果 | 对设计的影响 |
|---|---|---|
| 计费归属 | 同一 URL 上计费由 key 决定。用 Coding Plan 专用 key 调用后，额度查询接口（`GET https://open.bigmodel.cn/api/monitor/usage/quota/limit`，`Authorization` 填 key，两种写法都可以）返回套餐等级和两个积分窗口（5 小时、每周），已用值随调用增加。响应头和响应体里没有区分计费方式的字段。是否同时扣了账户余额，接口查不到，需要在控制台费用明细核对 | 智谱按量与 Coding Plan 用不同的 key 配成两个渠道（方案 §11 待定 1 的结论）；额度查询接口可供 M2 的只读额度展示使用 |
| `/v1/models` | 有效 key 时 200，返回 Anthropic 形态的模型列表（含 `glm-5.3`、`glm-5.3-flash`、`glm-5.3-flashx` 等） | 网关仍自己应答 |
| 错误体 | 有效 key 之后的错误是 Anthropic 形态：`error.type` 为 `invalid_request_error`，另有数字 `error.code`，`message` 形如 `[1211][模型不存在，请检查模型代码。][<request_id>]` | 原样转发 |
| `max_tokens` 超过上限 | 400，code `1210`：`max_tokens参数非法：限制数值范围[1,131072]` | 与 `maxOutputTokens: 131072` 一致；网关按元数据截断 |
| `anthropic-beta` | cc 2.1.309 的 7 个值加 `context-1m-2025-08-07` 一并发送：200 | `betaStrip: []` |
| thinking | 不带 `thinking` 参数时默认开启。传 `disabled` 时有时不再返回 thinking，有时仍返回 | 保持 `thinking: always-on` |
| thinking 签名 | 每个 thinking 块带 `signature`（24 位十六进制）；流式时 `content_block_start` 里是空串，随后 `signature_delta` 补齐 | — |
| 回放：本模型 thinking | 200 | — |
| 回放：工具调用轮缺 thinking（模拟 DeepSeek → GLM，cc 剥掉了 DeepSeek 的 thinking） | 200 | 不需要“历史不兼容”规则 |
| 回放：DeepSeek 形态的 thinking（签名为 UUID）/ 无签名 thinking | 200 | `thinkingReplay: passthrough` |
| 回放：`redacted_thinking` | 200 | `redactedThinking: supported` |
| GLM → DeepSeek（在 DeepSeek 上回放 GLM 形态签名的 thinking） | 200 | DeepSeek 仍为 `passthrough`；切换在工具调用循环中间时的行为见 §2 |
| 工具调用 id | `call_<24 位十六进制>`，符合 `^[a-zA-Z0-9_-]+$` | 不需要工具 id 编码 |
| **工具名 `ToolSearch`** | `tools` 中只要有名为 `ToolSearch` 的工具（与其 schema 无关），上游就只保留这一个工具，其余工具被静默丢弃（`count_tokens` 与实际调用的 `input_tokens` 都只计入 `ToolSearch`）。cc 2.1.309 每次都发送 `ToolSearch`，结果是 GLM 看不到 Bash、Read 等工具，回答“没有可用的 shell 工具”。去掉或改名 `ToolSearch` 后全部工具正常计入 | 新增 profile 字段 `toolStrip`，本渠道配置 `[ToolSearch]`：转发前去掉该工具（诊断 `tool_stripped`）。代价是 cc 的延迟加载工具（只列名字、要经 `ToolSearch` 取 schema 的那些）在本渠道不可用 |
| 图片（base64 PNG） | 64×64 纯色图：红色答 `Red`、蓝色答 `Blue`；同一问题不带图时答不出。带图比不带图多约 18 个 `input_tokens` | 图片确实被处理，`inputModalities: [text, image]` |
| 缓存 | 自动前缀缓存：第二次相同前缀 `cache_read_input_tokens` 5248，`input_tokens` 只含未命中部分。响应里没有 `cache_creation_input_tokens` 字段。cc 实际对话中相邻两轮不一定命中 | usage 原样返回 |
| `count_tokens` | `/v1/messages/count_tokens` 可用 | Coding Plan 渠道仍为 `countTokens: estimate`，不转发（方案 §6.3） |
| 流式事件 | `message_start`（`usage` 全为 0）→ `ping` → `content_block_start` …；实际 usage 只在 `message_delta` 里。JSON 带空格（`"type": "…"`）。响应头与首个事件一起到达（短请求约 4–5 秒） | 网关以 `message_delta` 的 usage 为准（契约测试覆盖） |
| 限流头 | 无 `retry-after` / `x-ratelimit-*` | — |
| 限流 / 并发错误（1302 / 1305） | 未测：触发需要超出套餐并发的请求量 | 原样转发，不重试 |
| 超长错误 | 未测：触发需要约 1M token 的请求 | 暂无改写规则；cc 收到的是上游原文 |

### 3.1 只跑到 401 阶段的用例（智谱、方舟 Coding Plan）

不需要有效 key 的用例（智谱按量与 Coding Plan 同一端点）：

| 项目 | 智谱 | 方舟 Coding Plan |
|---|---|---|
| 无认证头 | 401 `{"error":{"message":"Header中未收到Authorization参数，无法进行身份验证。","type":"1001"}}` | 401 `AuthenticationError`，`the API key or AK/SK in the request is missing or invalid` |
| 无效 key，`x-api-key` / `Bearer` | 两种头都被识别（同为 401 `令牌已过期或验证不正确`） | 两种头都被识别（同为 401 `The API key format is incorrect`） |
| 错误体格式 | `error.type` 是数字码字符串（如 `"1001"`、`"401"`），不是 Anthropic 错误类型 | `error.type` 为 `Unauthorized`，另有 `error.code` |
| `GET /v1/models` | **HTTP 200**，体为 `{"code":401,"msg":"令牌已过期或验证不正确","success":false}` | 401 |

方舟 Coding Plan 与智谱按量待补 key 后要跑的用例（与 DeepSeek 相同的 `probe.mjs` 用例集）：超长错误原文、thinking 签名与跨渠道回放、`redacted_thinking`、beta 拒收、缓存字段、限流错误码（智谱 1302 / 1305、方舟 429）、方舟 `output_config.effort` 是否让思维链混进正文（脚本已检测 `<think>` 标签）、图片（`image_color` 用例：纯色图答对颜色且 `input_tokens` 明显增加才算被处理）、`ToolSearch` 工具名是否同样导致其余工具被丢弃。

## 4. Claude Code CLI 2.1.309 请求基线

通过 `ANTHROPIC_BASE_URL` 指向本机记录型反代、再转发到 DeepSeek 抓取（临时 `CLAUDE_CONFIG_DIR`，不读用户 settings）。

- 启动时 `GET /v1/models?limit=1000`（带认证头、`anthropic-version`），之后 `POST /v1/messages?beta=true`。**路径带查询串**，网关按原样转发。
- 请求头：`authorization: Bearer <key>`、`anthropic-beta`（见 §2）、`anthropic-version: 2023-06-01`、`x-app: cli`、`user-agent: claude-cli/2.1.309 (external, sdk-cli)`、`x-claude-code-session-id`、`x-claude-code-prompt-id`、`x-stainless-*`。开启 `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` 后有 `x-claude-code-request-class: main | subagent | compaction`；子 agent 请求另有 `x-claude-code-agent-id`、`x-claude-code-agent-type: general-purpose`，并与主会话共用 session id。
- 请求体键：`model, messages, system, tools, metadata, max_tokens, thinking, context_management, output_config, stream`。
  - `thinking: {type: "adaptive", display: "omitted"}`，`output_config: {effort: "max"}`，`max_tokens: 32000`，`context_management: {edits: [{type: "clear_thinking_20251015", keep: "all"}]}`（对不认识的 `claude-gw-*` ID 也这样发）。
  - `system` 三块：计费头文本（`x-anthropic-billing-header: cc_version=…`，无 `cache_control`）、身份块、主提示（各带 `cache_control`）。
  - `messages` 中会出现 **`role: "system"` 的消息**（环境信息等，位于对话中间），DeepSeek 接受。网关的工具配对校验跳过这类消息。
  - `metadata.user_id` 为 JSON 字符串，键为 `device_id`、`account_uuid`、`session_id`。
- 对不认识的模型 ID，cc 在 stderr 打印 `[claude-code:unrecognized_model]`，不影响请求。
- `-c` 续接会话时 session id 不变，网关据此检测到用户切换（日志诊断 `switch`）。

## 5. 待补的抓包

桌面端内置 Claude Code 是否读取用户 settings：桌面端 3.6556.2 的代码中，主 Code 会话以 `settingSources: ["user", "project", "local"]` 启动 Claude Code（侧边对话等为 `[]`），即会读取用户级 `settings.json`（含其 `env` 块与 `modelSettings`）。这是代码层面的证据，仍待抓包确认。

**桌面端（Code 模式）基线**需要临时把桌面端第三方推理配置指向本机抓包代理，由使用者本人操作：

1. 备份：`cgw desktop backup`（复制 `~/Library/Application Support/Claude-3p/configLibrary/` 到 `~/.claude-gateway-backups/`）。
2. 启动抓包代理：`node scripts/m0/capture-proxy.mjs --listen 127.0.0.1:18080 --target https://api.deepseek.com/anthropic --out captures/desktop --duration-sec 1200`。
3. 在桌面端 Developer → Configure Third-Party Inference 中把 Gateway base URL 临时改为 `http://127.0.0.1:18080`（key 保持原来的 DeepSeek key），模型条目改用 `claude-gw-*` 形态，重启桌面端。
4. 在 Code 模式里依次做：普通对话、让它跑一个工具、起一个子 agent、在选择器中切换模型、`/compact`。
5. 恢复：`cgw desktop restore <备份目录>`，重启桌面端。
6. 需要确认的事项见[桌面端接入 §7](桌面端接入.md#7-m0-抓包要确认的事项)。
