# 会话管理与模型切换

日期：2026-10-27。状态：**讨论稿**，§6 的问题确定后并入[方案](方案-v0.1.md)的 M1 / M2。

本文回答两个问题：

- Claude Code（cc）原生如何处理“同一会话中途换模型”？
- 网关接入国产模型后，应在哪些地方补位，哪些地方必须让路给 cc 自己的机制？

---

## 0. 结论速览

1. **用户 `/model` 切换后，cc 仍把完整历史发给新模型，但会先在本地剥掉“别的模型产生的、带签名的 thinking 块和 redacted_thinking 块”。** 通过 `ANTHROPIC_BASE_URL` 接第三方网关时，这条剥离规则**总是生效**。没有签名的 thinking 块不会被剥。
2. cc 还有一层兜底：只要上游返回“thinking 签名无效”一类的 400，cc 就剥掉**全部** thinking 块，然后自动重试。网关如果把国产模型的同类错误映射成 cc 认得的文案，就能复用这条自愈路径。
3. 判断“是不是别的模型”，cc 依据的是每条 assistant 消息的 `message.model`，也就是网关在 `message_start` 里返回的值。所以**网关回写的 model 必须稳定**，建议原样回写客户端请求的模型名。
4. **网关自己做的路由切换，cc 完全不知情**：请求的 model 没变，cc 不会剥任何东西。这类切换必须由网关自己处理 thinking、工具 id、图片和缓存。
5. 识别会话不用解析请求体：cc 每个请求都带 `x-claude-code-session-id`，子 agent 请求还带 `x-claude-code-agent-id`。设置 `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` 后，还能拿到 `x-claude-code-request-class`（main / subagent / compaction / auxiliary …）和压缩相关的头。
6. 对 cc 不认识的模型名，cc 只用**一个全局上下文窗口**（`CLAUDE_CODE_MAX_CONTEXT_TOKENS`，默认 200K），但压缩窗口可以**按模型**设置（`/autocompact` 或 settings 的 `modelSettings`）。超长时，只有当报错文案是 cc 认得的 “prompt is too long” 一类，cc 才会做被动压缩。
7. Anthropic 的缓存按模型隔离，换模型后的第一轮必然全量未命中。国产模型同理（至少跨供应商时必然如此）。

**推荐的网关策略**：

- 会话状态以 `x-claude-code-session-id` 加 agent-id 为键。
- 用户主动切换交给 cc 处理，网关只做补位。
- 网关自动切换默认只在会话的第一个请求、或 cc 压缩之后发生，平时保持粘性。
- 跨模型的 thinking 用“签名来源登记 + 网关自签名”判断能否保留，不能保留就降级。
- 上下文和缓存问题，用 cc 认得的错误文案和配置片段解决，不在网关里自作主张。

## 2. cc 原生行为调研

### 2.1 `/model` 中途切换：历史与 thinking 怎么处理

**历史原样发送，但会剥离“异源”的签名 thinking。** [源码] cc 每次组装请求时，会对历史中的 assistant 消息做一次过滤：

- 对每条 assistant 消息，比较它的 `message.model` 和本次请求的模型。如果不同（按 cc 的模型身份归一化比较，并且该模型不在“本次请求的模型曾被服务端以某某模型名应答”的登记里），就视为**异源消息**。
- 异源消息里满足以下条件的块会被**删除**：`type == "redacted_thinking"`，或 `type == "thinking"` 且 `signature` 非空。没有签名的 thinking 块、text、tool_use 等都保留。
- 是否保留异源 thinking，由一个三值策略控制：`none`（全剥）、`upgrade`（只在同家族升级时保留）、`all`（全保留），对应埋点 `api_keep_thinking_on_model_change` 和 `api_keep_thinking_on_upgrade`。该策略**只在“第一方 Anthropic API 且没有自定义 base URL”时才可能不是 `none`**：源码里判定第一方的函数会检查 `ANTHROPIC_BASE_URL` 是否为 `api.anthropic.com`。也就是说，**接网关时固定为 `none`，换模型就剥**。

**兜底：签名报错后剥光重试。** [源码] 上游返回 400，且错误文案（去掉反引号、转小写后）包含以下任一时，cc 会认定是 thinking 签名问题：

- `signature in thinking block`
- `invalid data in redacted_thinking block`
- `thinking.signature` 加 `field required`
- （`thinking block` 或 `redacted_thinking`）加（`cannot be modified` 或 `invalid signature`）

认定之后，cc 剥掉**所有** assistant 消息中的 thinking 和 redacted_thinking；剥完为空的消息补一个 `[Thinking removed]` 文本块。然后自动重试，埋点为 `tengu_thinking_signature_strip_retry`，日志为 `[thinking] server rejected a thinking block; stripping all thinking blocks and retrying.`。

同一段错误处理还会识别 “thinking.type enabled/adaptive not supported”，自动在 `enabled` 和 `adaptive` 之间切换后重试。

[CL] 相关条目：

- `2.1.152`：“Fixed sessions getting stuck after a model or login switch left stale thinking-block signatures in history; now stripped proactively with a retry safety-net”。这就是上面“主动剥离 + 重试兜底”的由来。
- `2.1.282`：修复了 `/model` 等命令在 Claude 工作时执行导致早期 thinking 被丢的问题。
- `2.1.287`：修复了 Opus 5.5 和 Sonnet 5.5 之间切换（`/model`、`opusplan`）时改写早期 MCP 工具声明、进而丢掉早期 thinking 的问题。

**Anthropic 官方的跨模型签名规则** [文档]（[thinking 文档：Switching models mid-conversation 与 Preserved thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)）：

- 换模型时应**继续原样回传** thinking 块。一个 thinking 块只有产生它的模型和**一组固定的其他模型**能读，API 会**静默丢弃**目标模型读不了的块，不报错也不计费。方向有讲究，例如 Fable 5.1 能读 Opus 5.5 的块，反过来不行。
- 从 Fable 5.1 起，API 还会对每个 thinking 和 redacted_thinking 块做**前缀校验**：块之前的 `system`、`tools` 和消息有任何改动，这个块以及之后所有 thinking 块都失效。处理方式是返回 400，或者丢弃（可以用 `thinking.block_binding.prefix_mismatch_behavior` 选择）。2026-08-31 之后创建的账号默认强制校验。
- Sonnet 5.5 和 Haiku 5.5 的 thinking 块还与产生它的账号绑定。

**对网关的含义**：

- 接 Anthropic 官方时，cc 已经替我们剥了异源签名块，网关**不要再改动** thinking，也**不能**在前缀里插入任何东西，否则会触发前缀校验。
- 接国产模型时，“签名”是各家自己的东西（或者是网关伪造的），跨供应商一定不可读，必须由网关保证不把别家的签名发过去（见 §4.1）。

### 2.2 opusplan、子 agent 与后台小模型

- **opusplan** [文档]（[model-config：opusplan](https://code.claude.com/docs/en/model-config)）：plan mode 使用 `opus`，退出 plan mode 后自动切到 `sonnet` 执行。两阶段分别使用各自模型的上下文窗口。网关场景下，两阶段分别由 `ANTHROPIC_DEFAULT_OPUS_MODEL` 和 `ANTHROPIC_DEFAULT_SONNET_MODEL` 决定实际发出的模型名。
  - 从网关看，这就是**同一会话在两个模型名之间来回切换**，与 `/model` 切换走同一套“异源 thinking 剥离”逻辑。CL `2.1.287` 把 `/model` 和 `opusplan` 并列，可作佐证；opusplan 阶段切换是否确实走同一路径，[待 M0] 确认。
  - 文档还提到 Haiku 会话在 plan mode 会升级到 Sonnet。
- **子 agent** [文档]（[sub-agents：Choose a model](https://code.claude.com/docs/en/sub-agents)）：
  - 模型解析顺序：本次调用传入的参数 → agent 定义的 `model` frontmatter（`inherit` 表示跟随主会话）→ `CLAUDE_CODE_SUBAGENT_MODEL` → 主会话模型。
  - 内置的 Explore 等 agent 有自己的默认模型（文档表格列出 `claude-code-guide` 用 Haiku，`statusline-setup` 用 Sonnet）。`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` 可以强制所有子 agent 使用同一模型（`2.1.257+`）。
  - 子 agent 自 `2.1.198` 起继承主会话的 thinking 开关。
  - 子 agent 有**独立的 messages 历史**，与主会话的 thinking 签名互不相干。但它和主会话共用同一个 `x-claude-code-session-id`，靠 `x-claude-code-agent-id` 区分（见 §2.4）。
- **后台和辅助请求** [文档]（[costs：Background token usage](https://code.claude.com/docs/en/costs)、[llm-gateway-protocol 的 request-class](https://code.claude.com/docs/en/llm-gateway-protocol)）：会话标题、`--resume` 用的摘要、分类器、提示词建议等都属于 `auxiliary` 请求。提示词建议使用**会话当前模型**并复用其缓存，其余多为 Haiku 别名。它们与主会话共享 session id，但不属于主线程的历史。

### 2.3 上下文窗口、自动压缩与切到小窗口模型

**cc 认为的窗口** [文档]（[model-config：Correct the window for a gateway or custom model ID](https://code.claude.com/docs/en/model-config)）加 [源码]：

- 对 cc 认识的 Claude 模型名，使用它在 Anthropic API 上的窗口。cc **无法探测网关侧更小的限制**。
- 对不认识、且不以 `claude-` 开头的模型名（例如 `deepseek-v4-pro`），使用 `CLAUDE_CODE_MAX_CONTEXT_TOKENS`，未设置时为 200K（源码常量 200000）。带 `[1m]` 后缀的视为 1M。**这个变量是全局的，不分模型。**
- `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1`：对不认识的模型不做主动压缩，只在 API 返回 cc 认得的超长错误后才压缩。
- 通过网关的 `/v1/models` 做模型发现需要 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`。cc 只读 `id`、`display_name`、`description` 三个字段（[llm-gateway-protocol：Model discovery](https://code.claude.com/docs/en/llm-gateway-protocol)），**不会从网关读上下文窗口**。

**压缩阈值** [源码]：

- `有效窗口 = min(模型窗口, 压缩窗口设置) − min(模型最大输出, 20000)`。
- 达到 `有效窗口 − 13000` 时自动压缩。`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 可以把阈值改成百分比，但取两者中较小的值。
- 达到压缩阈值前 20000 时进入警告；达到 `模型窗口 − 预留 − 3000` 时直接阻断。

**压缩窗口来源的优先级** [文档]（[model-config：Set the auto-compact window](https://code.claude.com/docs/en/model-config)）：`CLAUDE_CODE_AUTO_COMPACT_WINDOW` → `--autocompact` → `/autocompact`（**按模型**保存到 user settings 的 `modelSettings`，`2.1.288+`）→ `autoCompactWindow`。结果都以模型窗口为上限。

**切到小窗口模型** [CL] `2.1.301`：“a conversation too long for the new model is now summarized by the previous model first”，并修复了这一步在未询问的情况下消耗额度的问题。这依赖 cc **知道**新模型的窗口更小。对网关上不认识的模型名，cc 只有一个全局窗口，**这条机制不会触发** [待 M0]。

**超长时的被动处理** [文档]（[errors：Prompt is too long](https://code.claude.com/docs/en/errors)）加 [源码]：

- cc 识别以下文案并触发被动压缩（`x-claude-code-compaction: reactive`）：`prompt is too long`、`input is too long for requested model`、含 `context window`、`input length and \`max_tokens\` exceed context limit`。
- 文档明确说明：**如果网关把错误改写成 cc 不认识的文案，cc 不会做这一步恢复。**
- cc 的回退模型也不会选窗口比当前更小的模型（[model-config：fallback](https://code.claude.com/docs/en/model-config)）。

### 2.4 会话标识：网关能否识别同一会话和切换事件

| 字段 | 何时发送 | 内容 | 证据 |
|---|---|---|---|
| `x-claude-code-session-id` 头 | 每个请求（含自定义 base URL） | 当前 cc 会话 ID | [文档] llm-gateway-protocol：Request headers；[源码] 默认头里还有 `x-app: cli` 或 `cli-bg` |
| `x-claude-code-agent-id` / `x-claude-code-parent-agent-id` 头 | 子 agent 发出的请求 | 子 agent ID（每次生成都是新的；agent team 成员使用稳定 ID） | [文档] 同上 |
| `metadata.user_id`（请求体） | 每个 Messages 请求 | **JSON 字符串**，含 `device_id`、`account_uuid`、`session_id`，以及可选的 `parent_session_id` | [源码] 构造该字段的函数；可被 `CLAUDE_CODE_EXTRA_METADATA` 扩展 |
| `x-claude-code-request-class` 头 | 设置 `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` 后才发（`2.1.273+`） | `main` / `subagent` / `workflow` / `compaction` / `auxiliary` | [文档] Gateway hint headers |
| `x-claude-code-agent-type` 头 | 同上，仅限子 agent 自己的回合 | `Explore` / `Plan` / `general-purpose` / `custom` / `teammate` / `fork` | 同上 |
| `x-claude-code-compaction` 头 | 同上，压缩请求本身 | `auto` / `manual` / `reactive` | 同上 |
| `x-claude-code-context-compacted` 头 | 同上，压缩后第一条主会话请求 | 同上的取值。文档说明“此前的前缀已不再使用，相关缓存可以丢弃” | 同上 |
| `x-claude-code-prompt-id` 头 | 同上（`2.1.283+`） | 用户一次提问的 UUID，子 agent 回合也沿用 | 同上 |

**结论**：

- 网关可以可靠地用 `(session-id, agent-id 或 "main")` 标识一条会话线，**不需要解析 `metadata.user_id`**（解析只作兜底）。
- **用户切换事件**：同一会话线上，请求体的 `model` 与上一个 main 请求不同。opusplan 的阶段切换也会表现为这种变化。
- **cc 自己在切换前后的动作**（例如切到小窗口前先用旧模型摘要）会表现为 `x-claude-code-compaction` 请求，需要开启 hint 头才看得见。
- cc 还提供 `PreModelSwitch` 和 `PostModelSwitch` 两个 hook 事件（[CL] `2.1.251`，[文档] hooks），可以拦截或确认切换。网关不需要依赖它们，但可以用来做“切换前提示重建缓存的成本”（§4.6）。

### 2.5 切换对缓存的影响

- [文档]（[cc prompt-caching：Switching models](https://code.claude.com/docs/en/prompt-caching)）：每个模型有自己的缓存。`/model` 切换后的下一轮会把整段历史当作未缓存输入，即使内容完全相同。缓存还热的时候，cc 在终端里切换前会让用户确认。
- [文档]（API prompt caching）：thinking 参数（模式、budget）和 `output_config.effort` 都会渲染进 prompt，改动会使消息级缓存失效。缓存还按 workspace 或组织隔离。
- [源码] cc 内部记录缓存失效原因，其中一类是 `model_changed`，其他还有 system prompt、tools、effort、thinking 等变化。
- 国产模型：各家缓存都是供应商内部的，**跨供应商不可能命中**；同一供应商内换模型是否共享缓存，[待 M0] 用 usage 实测。

## 3. 参考实现怎么做

| | CCR | dsh |
|---|---|---|
| 会话识别 | v2 从 `metadata.user_id` 的 `_session_` 后缀解析 session，用于取上一轮 usage 判断 longContext（调研 §2.1）。cc 现在的 `user_id` 已改成 JSON，这种解析方式已经过时 | 自有 Session 概念，不涉及 cc |
| thinking 跨模型 | v2 在 OpenAI 统一格式里携带 `thinking{content, signature}`；把 `reasoning_content` 转成 thinking 时**伪造签名**（`reasoning` / `forcereasoning` transformer 用 `Date.now()` 当 signature）。v3 只合并相邻的无签名块，不处理跨模型（调研 §2.5） | `readReplay` 按**目标模型**校验回放元数据，跨模型签名不可移植，直接降级丢弃并上报诊断（不含正文）（调研 §3.2） |
| 工具 id | v2 在 OpenAI 侧缺 id 时生成 `call_${Date.now()}_${i}`；server tool 使用 `srvtoolu_${uuid}` | 严格校验 tool_use / tool_result 配对 |
| 图片 | 用 MCP 视觉工具（fusion-vision）补齐 | 模型不支持图片时直接报 `UNSUPPORTED_CONTENT`；另有 image-offload 把旧图替换成路径文本 |

CCR v2 伪造签名的后果：cc 会把这些块视为“带签名”。用户 `/model` 切换时，cc 会按异源剥离，这是好事；但如果网关把同一会话路由到 Anthropic 官方，伪造的签名会引发 400，再进入 cc 的“剥光重试”，多耗一轮请求。

## 4. 网关侧设计

### 4.1 会话状态与切换分类

**会话键**：`sessionKey = x-claude-code-session-id + "/" + (x-claude-code-agent-id || "main")`。缺少头时，回退到 `metadata.user_id` 中的 `session_id`；两者都没有，则按无会话处理（不做粘性）。

**每条会话线保存的状态**（内存加可选 SQLite，只存元数据，TTL 默认 24h）：

- `lastRequestedModel`：上一个请求体里的 `model`，也就是 cc 视角下的模型。
- `lastTarget`：`{provider, upstreamModel, credentialId}`。
- `thinkingLedger`：签名指纹（sha256 前 16 字节）→ `{provider, upstreamModel}`。
- `lastInputTokens`：上一轮上游真实的 input_tokens 和缓存读写量。
- `imageDigests`：已转写的图片哈希列表（与 §4.4 共用）。

**切换分类**（每个请求开始时判断）：

| 类型 | 判断条件 | 谁负责 thinking 和历史清理 |
|---|---|---|
| 用户主动切换 | `requestedModel != lastRequestedModel`（含 opusplan 阶段切换） | cc 已剥离异源签名块。网关只处理 cc 剥不到的部分：无签名的 thinking、工具 id、图片 |
| 网关自动切换 | `requestedModel` 不变，但路由结果 `target != lastTarget`（规则命中变化、回退、key 切换到其他供应商；**同一模型换渠道也算**，例如 DeepSeek 官方换到方舟上的 DeepSeek，见[方案 §4.5](方案-v0.1.md#45-thinking--extended-thinking)） | **全部由网关负责**，cc 毫不知情 |
| 子 agent / 辅助请求 | agent-id 不同，或 request-class 为 `subagent` / `auxiliary` | 独立会话线，各自粘性，互不影响 |
| 压缩边界 | 带 `x-claude-code-compaction`，或 `context-compacted` | 压缩后的历史是新前缀，是**最便宜的换模型时机**（§4.7） |

### 4.2 跨模型的 thinking / reasoning_content

**原则**：

- 目标模型读不了的 thinking 绝不能发出去。
- 网关能判断“读得了”时就原样保留。
- 判断不了时宁可降级，也不赌 400。

**1. 回写 `message.model`：原样回写客户端请求的模型名**（推荐）。桌面端要求模型 ID 呈 Claude 形态，网关对外使用 `claude-gw-*` 这类 ID（见[桌面端接入 §6](桌面端接入.md#6-对网关设计的影响)），回写的就是这个对外 ID。

这样 cc 的异源判断就以“用户选的模型”为单位，用户切换时 cc 会正确剥离。它的代价正是 §0 第 4 点：网关自动切换对 cc 不可见，所以下面的第 2、3 条必须做。

**2. 签名来源判定**：

- **原生 Anthropic 兼容上游**（DeepSeek、GLM 等的 `/anthropic` 端点）返回的签名**不做任何改动**，只把指纹登记到 `thinkingLedger`，记录 `{provider, upstreamModel}`。
- **OpenAI 格式上游**的 `reasoning_content` 转成 thinking 块时，由网关**自签名**，格式为 `cgw1.<base64url(json{p,m,t})>.<HMAC-SHA256 截断>`，密钥只在网关本地保存。

自签名的好处：

- cc 会把这些块视为“带签名”，用户切换模型时会按异源剥离，与官方行为一致。
- 网关无需任何状态就能认出自己签发的块，并知道它来自哪个模型。
- 不会像 CCR 那样伪造成看似合法的 Anthropic 签名。

**3. 出站前的过滤**（对每个 thinking 和 redacted_thinking 块）：

| 块的来源（登记表或自签名解析结果） | 目标与来源的关系 | 动作 |
|---|---|---|
| 同一 provider、同一 upstreamModel | 相同 | 原样发送 |
| 同一 provider、不同模型 | 由 profile 声明的 `thinkingReadableFrom` 决定 | 声明可读就保留，否则剥离 |
| 不同 provider | — | 剥离。OpenAI 目标需要 `reasoning_content` 时，见下一条 |
| Anthropic 官方 | 目标是官方 | 原样发送，跨模型交给 API 自己静默丢弃（官方规则） |
| 登记表查不到，又不是 `cgw1.` 前缀（网关重启丢了状态，或历史来自直连） | 目标是官方 | 原样发送 |
| 同上 | 目标不是官方 | **剥离** |

- 剥离时沿用 cc 的做法：消息变空就补一个 `[Thinking removed]` 文本块。剥离的块数记入诊断。
- 规则不使用“改成纯文本”：那等于把 A 模型的思考塞给 B 模型当作正文，会污染上下文。需要时可以作为 profile 选项（Q-S3）。

**4. OpenAI 格式目标对 `reasoning_content` 的要求**（DeepSeek 在带工具的 thinking 模式下要求回填，调研 §3.3）：

- 来源是同模型的自签名块：还原原文填入 `reasoning_content`。
- 来源是异源：填空字符串。这是 pi-ai `requiresReasoningContentOnAssistantMessages` 的做法。

**5. 错误自愈**：上游返回与签名或 thinking 相关的 400 时，网关**改写为 cc 认得的文案**，例如 `messages.N.content.M: Invalid \`signature\` in \`thinking\` block`，类型为 `invalid_request_error`，让 cc 进入“剥光重试”。这是兜底手段；正常情况下第 3 条已经避免了此类错误。

**6. 不在前缀里做任何新增改动**：

- 第 3 条只删除块，删除点及之后的缓存必然失效，这是可以接受的代价。
- 但绝不在前缀里插入内容。对 Anthropic 官方目标完全不改动 thinking，避免触发 Fable 5.1 起的前缀校验。

### 4.3 工具调用 id

- Anthropic 要求 `tool_use.id` 匹配 `^[a-zA-Z0-9_-]+$`。OpenAI 格式上游的 id 风格各异：`call_xxx`；有的家族会带 `.` 或 `:` 之类的字符（例如 Kimi 常见的 `functions.<name>:<idx>` 形态，[待 M0] 逐家核实）；有的甚至缺省。
- **推荐无状态的可逆编码**：
  - 上游 id 合法且不以 `toolu_` 开头时，原样使用。
  - 不合法时编码为 `toolu_cgw_<base32(原 id)>`；发回同一个上游时解码还原。
  - 上游缺 id 时生成 `toolu_cgw_<随机>`，发回时如果上游要求 id，就用这个值。
- 跨供应商切换后，历史中的 tool_use id 发给新上游：
  - 新上游是 Anthropic 兼容端点：id 只需要合法，并在消息内配对，原样发送即可。
  - 新上游是 OpenAI 格式：tool_call id 原样作为字符串传递，部分家族对格式有要求时再按 profile 转换。
- 不管怎么切换，都要校验 tool_use 和 tool_result 的配对（dsh 做法）。配对不完整时直接返回 400，并给出明确原因。

### 4.4 图片：切到不支持图片的模型

- cc 不会因为换模型而处理历史里的图片。历史中的 `image` 块会原样发给新模型。
- 网关按目标模型的 `inputModalities` 判断：
  - 支持图片：原样发送。
  - 不支持：走[方案 §7.3](方案-v0.1.md#73-多模态增强看图)的**转写**，用视觉模型生成描述并替换成文本块，结果按 `sha256(图片) + 视觉模型 + 提示词版本` 缓存。这样**同一张图在后续每一轮、甚至切回原模型前后，生成的文本都完全一致**，避免反复转写和反复破坏缓存。
  - 未启用转写时，返回 400 并说明“目标模型不支持图片”，不静默丢图。

  这里的错误文案是功能性的校验错误，具体措辞在实现时再定。
- 切回支持图片的模型时，默认**继续使用转写后的文本**（同一会话线内保持一致，利于缓存）。可选“切回时恢复原图”，代价是一次缓存失效（Q-S4）。

### 4.5 上下文窗口不一致

问题出在两侧：cc 对不认识的模型只有一个全局窗口，而各国产模型的窗口差别很大（DeepSeek 1M，其他多为 128K–256K，[待 M0] 逐个核对）。

1. **配置侧（M1 交付）**：网关的 `cgw cc` 或 `cgw print-cc-settings` 生成 settings 片段：
   - `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 设为**会话内可能用到的最大窗口**。
   - 按模型写入 `modelSettings.<model>.autoCompactWindow`，等价于对每个模型执行一次 `/autocompact`，让小窗口模型提前压缩。
   - 两者的组合效果，以及 `modelSettings` 对不认识的模型名是否生效，[待 M0] 验证。
   - 备选：设置 `CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1`，完全依赖网关返回的超长错误来触发被动压缩。
2. **网关侧（M1 必做）**：请求的估算 token 加 `max_tokens` 超过目标窗口时，**不转发**，直接返回 `400 invalid_request_error`，文案为 `prompt is too long: <N> tokens > <M> maximum`，保证 cc 能识别并做被动压缩。同理，上游返回的超长错误统一改写成这个格式。
3. **路由侧**：网关自动切换（回退、longContext 以外的规则）**只能选窗口不小于当前会话 `lastInputTokens` 的目标**，这与 cc 回退的规则一致。没有合适的目标就不切换。
4. **用户切到小窗口模型**：交给 cc。若 cc 没有提前压缩，第 2 条会返回超长错误，cc 进入被动压缩，压缩请求带 `x-claude-code-compaction: reactive`。这个压缩请求**发给哪个模型**是关键：如果发给新的小窗口模型，摘要本身也可能超长。网关对 `compaction` 类请求的策略是：如果会话线的 `lastTarget` 窗口更大，就把摘要请求路由回 `lastTarget`。这与 cc `2.1.301` 的“先由旧模型摘要”思路一致（需要 hint 头，Q-S5）。

### 4.6 缓存失效的成本提示

- 网关在每次切换（两类都算）时记录 `switch` 诊断事件：会话线、原目标和新目标、`lastInputTokens`、预估重建成本（`lastInputTokens × (新模型未缓存输入单价 − 缓存读单价)`，单价来自 provider 元数据）。
- 在 `cgw` 的 CLI 或统计中按会话汇总，供事后分析。
- **可选**：提供一个 `PreModelSwitch` hook 脚本，由它向网关查询当前会话的预估重建成本，再决定是否让 cc 弹出确认。cc 原生只在缓存仍热、且对官方模型时才确认。

  hook 输出的文字会显示给用户，文案需要单独评审后再加（Q-S6）。

### 4.7 路由自动切换与会话粘性

- **默认粘性**：主会话线第一次路由确定 `lastTarget` 后，后续请求只要 `requestedModel` 不变就沿用。这样保护缓存、签名和工具 id 的一致性。
- **允许网关自动切换的时机**，按代价从低到高：
  1. 会话线的第一个请求。
  2. 压缩之后的第一个主请求（`x-claude-code-context-compacted`），此时前缀已经换新，缓存本来就要重建。
  3. 首字节前的故障回退（429、5xx、超时、连接失败），只选窗口足够的目标。
  4. 用户在 cc 里 `/model` 换了模型名，此时按新名字重新路由。
- **longContext 场景**：会话增长超过阈值时，“切到长上下文模型”会导致一次全量未命中。推荐优先建议用户在 cc 侧调低压缩窗口；如果确实要切，就在压缩边界切（Q-S2）。
- **子 agent 和辅助请求**：各自独立路由，例如 Explore 走便宜模型。它们和主会话线的缓存本来就不共享，不影响主会话的粘性。
- 同一供应商内**按 key 切换**（多 key 池）也会影响缓存（缓存通常按账号隔离），因此 key 也在粘性范围内，只在故障或额度耗尽时更换。

## 6. 开放设计问题

- **Q-S1 签名处理方案**：推荐“原生签名只登记指纹 + OpenAI 上游由网关自签名 `cgw1.`”。备选 A 是对所有签名都加网关信封（判断最精确，但会改写原生签名，历史与网关强绑定，直连官方时失效）；备选 B 是不登记，跨 provider 时一律剥光（最简单，但浪费同 provider 内本可保留的推理）。
- **Q-S2 网关自动切换的范围**：只在会话首请求、压缩边界和故障回退时切换（推荐），还是允许按 token 阈值随时切到 longContext 模型？
- **Q-S3 剥离 thinking 时**：直接删除（推荐），还是允许按 profile 转成纯文本，把推理带给新模型？
- **Q-S4 图片转写后切回视觉模型**：继续使用文本（推荐，利于缓存），还是恢复原图？
- **Q-S5 是否要求 cc 侧开启 `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`**：开启后网关能识别压缩、子 agent 和辅助请求，路由更准，推荐开启。其余功能在不开启时也能工作，只是降级。
- **Q-S6 缓存重建成本提示**：只记日志（推荐先这样），还是提供 `PreModelSwitch` hook 在 cc 里提示？如果要提示，提示文案需要单独评审。
- **Q-S7 会话状态的持久化**：只放内存（网关重启后按“来源未知”处理，降级更多），还是落到 SQLite（只存元数据和签名指纹）？
- **Q-S8 `message.model` 回写**：原样回写客户端请求的模型名（推荐），还是回写真实上游模型名（显示直观，但需要确认 cc 的“服务端模型登记”在网关场景下是否可靠，否则可能每一轮都判为异源）？
