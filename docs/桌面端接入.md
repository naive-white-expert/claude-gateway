# Claude 桌面端接入

日期：2026-10-27。本文说明 Claude 桌面端（Code 模式）经“第三方推理（3P）/ Gateway”接入本网关时，桌面端如何读取配置、选择模型、发现模型、估算上下文窗口和触发压缩，以及网关要怎么配合。Claude Code CLI 的差异放在 §5。

桌面端是本项目的**第一接入对象**，CLI 同时支持。

## 0. 结论速览

1. **模型 ID 必须“看起来是 Claude”**。在 `inferenceProvider: "gateway"` 下，桌面端会检查每个模型 ID：
   - ID 里命中了内置的非 Anthropic 模型片段表（`deepseek`、`glm`、`kimi`、`qwen`、`doubao`、`seed-`、`minimax`、`ark-code` 等）就**不通过**。
   - 没命中的 ID，还必须包含 `claude`、`anthropic` 或档位词（`sonnet`、`opus`、`haiku`、`fable`、`mythos`）才通过。
   - 不通过的 `inferenceModels` 条目会被**移出列表**。
   - 所以 `deepseek-v4-pro` 这类真实名不能直接作为桌面端模型 ID，`claude-deepseek-v4` 也不行（命中了 `deepseek`）。
2. **模型发现走 `GET {base}/v1/models`**。网关可以在每个模型对象上返回以下字段，桌面端会读取：
   - `display_name`、`description`；
   - `anthropic_family_tier`、`is_family_default`；
   - `supports_1m`，或者 `max_input_tokens ≥ 1000000`。
3. **上下文窗口是桌面端推断出来的**，不是从上游读的：
   - 不认识的模型 ID 按 200K 处理；
   - `supports1m` / `prefer1m` 的条目按 1M 处理。
   - 只有当上游的超长错误被 Claude Code 识别时，才会触发被动压缩。
4. **桌面端启动的 Claude Code 进程只继承白名单内的环境变量**。终端里设置的 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 等变量**不会**被带进去；压缩窗口要通过 Claude Code 读取的 settings 文件或桌面端的模型声明来设置。
5. **典型问题**：上游返回的是非 Anthropic 措辞的超长错误（例如 DeepSeek 的 `This model's maximum context length is … tokens`），Claude Code 无法把它识别为“超长”，于是不压缩，会话卡在连续 400。网关在这里做一处**必要的兼容改写**（§4.3）。

## 2. 桌面端 3P 配置

### 2.1 配置存放与生效

- macOS 上，3P 模式使用独立的数据目录 `~/Library/Application Support/Claude-3p`，日志在 `~/Library/Logs/Claude-3p`。
- 配置项保存在该目录下的 `configLibrary/<id>.json` 中；当前生效哪一份，由 `configLibrary/_meta.json` 的 `appliedId` 决定。根目录 `claude_desktop_config.json` 中的 `deploymentMode: "3p"` 标识 3P 模式。[代码]
- 也可以在 **Developer → Configure Third-Party Inference…** 中编辑，或通过 MDM 下发。[文档]

### 2.2 与网关相关的键

| 键 | 含义 | 网关侧要求 |
|---|---|---|
| `inferenceProvider` | 设为 `"gateway"` | — |
| `inferenceGatewayBaseUrl` | 网关根地址，桌面端在其后拼接 `/v1/messages`、`/v1/models` | 公网 HTTPS 地址 |
| `inferenceCredentialKind` | `static`（静态 key）、`helper-script`（凭据脚本）、`interactive` / `external-idp`（OIDC） | 本项目用 `static` 或 `helper-script` |
| `inferenceGatewayApiKey` | 静态 key | 填网关签发的 key（不是上游 key） |
| `inferenceGatewayAuthScheme` | `bearer`（默认）或 `x-api-key` | 网关两种头都接受 |
| `inferenceModels[]` | 显式模型列表，第一条为默认 | 见 §2.3 |
| `modelDiscoveryEnabled` | 是否调用 `/v1/models` | 见 §3 |
| `modelPrefer1mContext` | 凡是声明了 1M 的模型都只显示 1M 选项 | — |
| `defaultModelEffort` | 默认模型的初始 effort | — |
| `inferenceCustomHeaders` | 每个推理请求附加的头 | — |
| `inferenceStreamIdleTimeoutSec` | 只收到 ping 时额外等待的秒数（默认 300） | 网关在长思考期间发 `ping` |

### 2.3 `inferenceModels` 条目

| 字段 | 含义 |
|---|---|
| `name` | 模型 ID，即**桌面端发给网关的 `model`**。必须通过 §2.4 的检查 |
| `labelOverride` | 显示名，只影响显示 |
| `supports1m` / `prefer1m` | 提供 1M 选项；`prefer1m` 表示只显示 1M 选项。`name` 带 `[1m]` 后缀等价于 `supports1m` |
| `anthropicFamilyTier` + `isFamilyDefault` | 声明该条目代表哪个档位（`haiku` / `sonnet` / `opus` / `fable` / `mythos`）。Code 会话里的 `sonnet` 等档位别名会解析到这里 |
| `maxEffort` | 该模型允许的最高 effort（`low`…`max`） |
| `minDesktopVersion` | 最低桌面端版本 |

[代码] 中 `inferenceModels` 条目的 schema 只要求 `name` 非空。但加载配置时，`gateway` provider 还会做 §2.4 的检查。

### 2.4 模型 ID 检查（关键约束）

[代码] 桌面端对 `gateway`（以及 `mantle`）provider 的模型 ID 做如下判断：

1. ID 转小写后，命中内置的**非 Anthropic 片段表** → 不通过。片段表包括：

   `ark-code`、`deepseek`、`doubao`、`glm`、`gpt`、`kimi`、`minimax`、`moonshot`、`qwen`、`seed-`、`hunyuan`、`ernie`、`mimo`、`stepfun`、`codex`、`\bds-`、`dpsk`、`\bk2\.`、`\bm2\.`、`llama`、`gemini`、`mistral`、`yi-`、`phi-`、`nova-`、`abab` 等。
2. 否则，ID 是档位词本身（如 `sonnet`、`opus-4`），或者包含 `claude`、`anthropic`、档位词之一 → 通过。
3. 其余 → 不通过。

不通过的后果：

- `inferenceModels` 中的该条目被移出列表，日志为 `inferenceModels: "<id>" is not an Anthropic model and was removed from the list`。错误提示要求 ID 是“referencing an Anthropic model”的网关路由名。
- 档位 pin（`ANTHROPIC_DEFAULT_*_MODEL`）的取值如果命中片段表、又不含 `claude` 或档位词，会被忽略，日志为 `value matches a known non-Anthropic model fragment; ignoring`。
- 模型发现返回的条目：ID 通过检查，**或者**带合法的 `anthropic_family_tier`，才会保留。官方文档的说法是“Auto-discovery shows only models whose IDs are recognizably Claude”；而代码显示带档位标记的非 Claude ID 也会保留。二者不一致，[待 M0] 实测。

参考实现的做法：CCR 把真实目标模型编码进 ID，格式为 `anthropic/claude-ccr-h<目标模型名的 hex>`。hex 只含 `0-9a-f`，不可能拼出片段表里的词，从而保证能通过检查。

## 3. 模型发现

[代码] 加 [文档]：

- 请求：`GET {inferenceGatewayBaseUrl}/v1/models?limit=1000`，翻页时带 `after_id`，最多 3 页。请求带认证头和 `anthropic-version: 2023-06-01`，超时约 10 秒。
- 响应：要求 `data` 是数组；翻页依据 `has_more` 和 `last_id`。
- 读取的字段：`id`、`display_name`、`description`（截断到 100 字符）、`anthropic_family_tier`、`is_family_default`、`supports_1m`、`max_input_tokens`（≥ 1,000,000 视为支持 1M）、`max_effort_level`。
- 什么时候不调用：
  - `inferenceModels` 中**全部**是完整 ID 时，自动跳过；
  - `modelDiscoveryEnabled: false` 时不调用；
  - 列表里含裸档位别名（如 `sonnet`）时必须保持发现开启，否则别名无法解析。
- 失败时回退到 `inferenceModels` 列表。端点挂起会让启动时的模型列表最多延迟 10 秒。

网关的做法：`/v1/models` 直接由网关应答，返回对外模型 ID（§4.1）及以上字段，不做重定向。CLI 的模型发现需要 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`，超时 3 秒，只读 `id`、`display_name`、`description`。

## 4. 上下文窗口、压缩与错误

### 4.1 桌面端假设的窗口

[文档]（gateway → Context window and compaction）：

- 经网关时，会话无法从上游读取真实窗口，只能按模型 ID 和选择器条目推断：
  - **普通条目**：Claude Code 认识的原生 1M 模型按 1M；其余（包括不认识的 ID）按 200K。
  - **1M 条目**（`supports1m` 的 1M 变体，或者 `prefer1m` / `modelPrefer1mContext`）：一律按 1M。
- 网关或上游接受的窗口比会话假设的小时，超过限制的请求会失败；**只有上游的超长错误原样到达**会话，会话才会压缩并重试。
- 选择 1M 条目时，请求会带 `anthropic-beta: context-1m-2025-08-07`，网关必须接受这个值。

[代码]：

- 桌面端启动 Claude Code 时，如果环境里还没有 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 和 `CLAUDE_CODE_DISABLE_1M_CONTEXT`，会按自己对该模型的判断写入 `CLAUDE_CODE_MAX_CONTEXT_TOKENS`。
- 桌面端会把 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`、`CLAUDE_CODE_MAX_CONTEXT_TOKENS` 记入会话启动日志。

### 4.2 压缩窗口怎么设置

- [代码] 桌面端启动 Claude Code 时，只从用户 shell 环境中继承一个**白名单**：`PATH`、`CLAUDE_CONFIG_DIR`、`CLAUDE_CODE_TMPDIR`、`CLAUDE_CODE_EFFORT_LEVEL`、TLS 相关变量（`NODE_EXTRA_CA_CERTS` 等）、OTEL 相关变量等。**`CLAUDE_CODE_AUTO_COMPACT_WINDOW` 不在白名单里**，所以在终端里设置它对桌面会话无效。
- 可行的设置途径：
  1. Claude Code 自己读取的 settings 文件：user settings 的 `env` 块、`autoCompactWindow`，或者按模型的 `modelSettings.<模型>.autoCompactWindow`（取值 100000–1000000，或 `"auto"`）。桌面端启动的 Claude Code 是否读取用户目录下的 settings，[待 M0] 确认。
  2. 在桌面端模型条目上声明 `supports1m` / `prefer1m`，让会话按 1M 假设窗口。
  3. managed settings。
- 网关侧的配合：`cgw` 生成桌面端配置片段时，**同时**生成对应的 Claude Code settings 片段（按模型的压缩窗口），并在文档里注明以上前提。

### 4.3 超长错误：典型问题与网关的必要改写

**现象**（非 Anthropic 上游的典型问题）：

1. 桌面 Code 会话用的是窗口接近 1M 的国产模型，桌面端也按 1M 假设窗口。
2. 会话增长后，“输入 + 预留输出”超过了上游的真实上限，上游返回 400：
   `This model's maximum context length is N tokens. However, you requested M tokens (… in the messages, … in the completion) …`
3. Claude Code 的超长错误识别（`prompt is too long`、`input is too long for requested model`、含 `context window`、`input length and \`max_tokens\` exceed context limit`，见[会话管理与模型切换 §2.3](会话管理与模型切换.md#23-上下文窗口自动压缩与切到小窗口模型)）匹配不到这段措辞，错误被归为未知。
4. 结果：不压缩、不重试，之后的每一轮都是同样的 400，会话无法继续。

**官方要求与网关的取舍**：

- 官方文档要求网关“原样转发上游的状态码和错误体”。这对 Anthropic 措辞的上游是对的；对措辞不同的国产上游，原样转发恰恰会导致上面的问题。
- 因此网关的规则是：
  - 上游错误已经是 Claude Code 能识别的措辞 → **原样转发**。
  - 上游返回的是已知的、非 Anthropic 措辞的超长错误 → 改写为 `400 invalid_request_error`，消息为 `prompt is too long: <请求 token 数> tokens > <上限> maximum`。保留原始错误摘要，并写入诊断。
  - 这是本网关的**必要兼容改写**之一（[方案 §1.2](方案-v0.1.md#12-纯透传原则)）。
- 另外，网关在转发前预估一次 token：确定会超出该“模型 × 渠道”的上限时，直接返回同样的超长错误，省掉一次必然失败的上游调用。

**验收**（M1）：在桌面 Code 会话中构造超长对话，确认会话自动压缩并继续；网关日志里能看到这次改写的诊断。

### 4.4 usage 与流式

[文档]：

- **原样返回上游的 `usage`**，包括 `cache_creation_input_tokens` 和 `cache_read_input_tokens`。会话据此计算上下文用量，缺了缓存字段就会少算，导致超过上限之前不压缩。
- 流式响应不缓冲，转发上游的 `ping`。只有 ping 的响应，会话大约接受 5 分钟，再加 `inferenceStreamIdleTimeoutSec`。压缩请求携带整段对话，耗时最长，网关和反代的超时都要大于最慢的完整响应。

## 5. 与 Claude Code CLI 的差异

| 维度 | 桌面端（Code 模式） | CLI |
|---|---|---|
| 配置来源 | `configLibrary` 中的 3P 配置（或 MDM） | 环境变量和 settings 文件 |
| Claude Code 版本 | 桌面端内置并固定版本，放在 3P 数据目录的 `claude-code/<版本>/` 下 | 用户自装的版本 |
| 环境变量 | 桌面端构造：`ANTHROPIC_BASE_URL`、凭据、`ANTHROPIC_CUSTOM_HEADERS`、档位 pin、`CLAUDE_CODE_MAX_CONTEXT_TOKENS` 等；shell 环境只继承白名单 | 继承 shell 环境 |
| 模型 ID | 必须通过 §2.4 的检查 | 任意字符串；不认识的 ID 按 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 或 200K 处理 |
| 模型发现 | 默认会调用（全部为完整 ID 时跳过），10s，读取档位、1M、effort 字段 | 需要 `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`，3s，只读 id / 名称 / 描述 |
| 窗口与压缩 | 由模型条目（`supports1m` 等）和桌面端写入的 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 决定 | 由环境变量和 settings 决定 |
| 实验性 beta | 网关部署下，默认关闭 tool search 及其他实验性 beta 头 [文档] | 默认开启（可用环境变量关闭） |
| 会话标识头 | 与 CLI 相同（同一个 Claude Code）[待 M0] | `x-claude-code-session-id` 等 |
| 沙箱策略 | 桌面端以 managed settings 的形式注入 sandbox 策略 [待 M0] | 用户自己的 settings |

## 6. 对网关设计的影响

1. **对外模型 ID 采用“Claude 形态”的网关 ID**，代替模型真实名：
   - 默认格式为 `claude-gw-<别名>`，例如 `claude-gw-flash`、`claude-gw-pro`；真实模型和渠道通过 `display_name` / `labelOverride` 展示。
   - 别名由用户配置。网关**加载配置时就用与桌面端相同的规则校验**（内置一份片段表，标注来源的桌面端版本）；不通过时拒绝启动，并给出原因。
   - 也允许使用 Claude 真实模型 ID 作为别名（例如 `claude-sonnet-4-6`）。代价是 Claude Code 会按那个 Claude 模型的能力假设处理，包括窗口、thinking 类型、effort 档位。这适合想让某个档位直接映射到国产模型的场景。
   - CLI 和桌面端使用**同一套对外 ID**，便于两边共用会话和配置。
2. **`/v1/models` 返回桌面端所需的全部字段**：`id`、`display_name`、`description`、`anthropic_family_tier`、`is_family_default`、`max_input_tokens`、`supports_1m`、`max_effort_level`。
3. **`message.model` 回显客户端请求的对外 ID**：Claude Code 按 `message.model` 判断历史消息是否“异源”（[会话管理与模型切换 §2.1](会话管理与模型切换.md#21-model-中途切换历史与-thinking-怎么处理)）。回显对外 ID 可以保证：用户在桌面端切换模型时，判断以对外 ID 为单位；网关内部换渠道时，由网关自己处理（会话专题 §4）。
4. **窗口声明要一致**：对外 ID 的 `max_input_tokens` / `supports_1m`、桌面端条目的 `supports1m`，以及 Claude Code settings 中的压缩窗口，由 `cgw` 从同一份“模型 × 渠道”元数据生成，避免三处不一致。
5. **错误改写**：只改写已知的非 Anthropic 超长措辞（§4.3）。

## 7. M0 抓包要确认的事项

- 桌面 Code 会话发给网关的请求：`model` 取值、请求头（会话头和 hint 头是否发送）、`anthropic-beta` 取值。
- 启动 Claude Code 时的实际环境与参数：`CLAUDE_CODE_MAX_CONTEXT_TOKENS` 的取值，managed settings 的内容，是否读取用户目录下的 settings。
- 模型发现：带 `anthropic_family_tier` 的非 Claude ID 是否真的出现在选择器中。
- 使用 `claude-gw-*` 这类 Claude Code 不认识的 ID 时，thinking / effort 参数如何发送。
- 构造超长对话：确认改写后的错误能触发桌面端的被动压缩。
